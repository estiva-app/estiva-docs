Where a link sits decides how it draws

A brief for Miky and Katerina · 15 Oct 2026 · Widgets 2 · it would replace a decision you both made on 13 Oct

The question

Should a link's place decide how it looks — a chip inside a sentence, a row when it is alone on its line, and one card under the message added for you when the message links a single file — instead of the author choosing chip, row or card for each link?

Today

Every link draws as a small chip, even alone on its line. To show more, you open the chip's menu and choose a row or a card, which draws under the message; you can change it after sending. Peek's message box lets you choose; Ship draws the choice but its comment box can't make one; Leaf has no cards yet.

That was Katerina's proposal in PEE-2's thread (5 Oct) — simply displaying the inline (chip) variant instead by default, with none, compact or detailed card — and Miky agreed when Widgets was shaped on 13 Oct. It is an Accepted decision today.

On 15 Oct, after the widget prototype, Miky proposed a simpler model:

Chip that can be placed inline inside a sentence · compact which acts as a single row · detailed which acts as card attachment … What if we allow compact row as a block (similar to heading) inside the conversation … the detailed would be only as attachment … we would always add the attachment, but the user would have option to remove similarly like in Slack. I feel that from user perspective this is easier than pushing user to choose between 3 formats.

In the WID-2 session he narrowed it: the card is added only when the message links exactly one file, removed with ✕, and old messages drawing differently under the new rule is fine.

Why it reaches beyond this ticket

  • The rule for every app. Today the protocol says a link's place never matters: not a reference alone on its line gives a card. This makes place part of how any Estiva-compatible app reads a message — Peek, Ship, Leaf and an outside company's client alike.
  • Documents too. Ship descriptions, Peek's panel and Leaf pages have no area under them, so the rule has to say what a document does instead.
  • Door: with the recommended option it is two-way. Nothing new goes into messages: the row is a reading rule, and the default card is today's card choice, written for you at send. Undoing it is a protocol text change plus each app's drawing code; messages already sent go back to drawing the old way. The option that writes a new "row" mark into messages is one-way: every reader must understand it forever.

The picture: a message under the new model

Options

A. The place decides, and the row is a reading rule (recommended)

  • Miky and Katerina see: you type or paste; a link in a sentence is a chip, a link on its own line becomes a row as you write. If the message links exactly one file, that file's card appears under the box; ✕ takes it away. There is no "choose a layout" step anywhere in a message.
  • An outside company: its app adds one reading rule — a line that is only a link draws as a row — and has nothing new to write. A message from any plain Nostr client draws the same way.
  • Locks in: a link alone on its line is always a row; to keep it a chip you put a word beside it. Old messages whose lone link was a chip now draw a row (Miky: fine).

B. The place sets the default, and a mark in the message records each row

  • Miky and Katerina see: the same as A while writing, plus a menu on a row to turn it back into a chip. Old messages stay exactly as they were sent.
  • An outside company: must write the new mark to get rows; a message from any other client shows chips everywhere.
  • Locks in: a new value in every message from now on, that every reader must understand forever.

C. Keep today: the author chooses for each link

  • Miky and Katerina see: every link a chip; a row or a card only when you choose it from the chip's menu; no card added for you. Katerina's model as accepted on 13 Oct.
  • An outside company: builds the three-way choice to match.
  • Locks in: nothing new; Miky's 15 Oct concern stays — three formats to choose from on every link.

A second, smaller question: a message that is just one link

Under A, a message that is only one link, alone on its line, links exactly one file — so it gets both a row and a card of the same file.

Recommendation: 1. The rule is one sentence for any reader: a file with a card under the message draws no row in it. A chip inside a sentence still draws, because the sentence needs its words.

Documents: descriptions and Leaf pages

A document has no area under it, so no card is ever added for you. The place rule is the same: a chip in a sentence, a row alone on its line. A link alone on its line can be switched to its card from the chip's menu, and the card takes that line's place — Miky's 15 Oct answer for Leaf (a link is either an inline chip or rendered as a block, with the widget's card as that block), here applied to Ship and Peek's panel too, since they read the same document format.

How others do it

  • Slack unfurls a link under the message and the author removes it with ✕; the removal is stored on the message. That is A's card.
  • Discord draws embeds under a message; suppressing them is a flag on the message — again only the removal is data.
  • Notion turns a link mid-sentence into a mention, and a link pasted on an empty line offers mention, bookmark (a row) or embed: place sets the default, and the choice is stored as a block — that is B. It works there because one company draws every page; on an open protocol each reader would have to learn the mark.
  • Linear turns a pasted issue link into an inline mention; Miky pointed to it on 5 Oct.
  • Nostr clients already decide on their own how to draw a reference; nothing upstream records a layout.

Recommendation

A, with the card replacing the row for a single lone link (1), and the document rule above.

The protocol reason: how a link looks is a reader's job, and the only thing the author actually decides — whether the one card is there — is the only thing that goes on the wire, as it already does today. An outside company gets the simplest deal: one reading rule and nothing new to write. The person reason is Miky's own: writing a message never asks you to pick a format, and what you typed is what people see. The cost is that a lone link can't stay a chip and old messages change look; Miky has said the second is fine. If keeping a chip on its own line turns out to matter, B is the way back — at the price of a mark in every message.

Katerina: this replaces your 13 Oct model (every link a chip, the author picks a card). Does it keep what you wanted from it — the URL never shown raw, the chip by default inside text?

Checked

  • Today's rule: no card unless chosen, not a reference alone on its line — protocol spec §13.6.2 on estiva-docs origin/main (f71d619), decided 13 Oct.
  • ✕ after sending works on today's wire: a card can be removed by an edit, and an edit that only removes a card is not marked edited (spec conformance C20).
  • Peek's message box writes the card choice, and its edits carry the whole set of cards (peek-app origin/main, useFileConversation.ts). Ship draws cards but its comment box can't choose one (Widgets' Later list). Leaf has no card code on origin/main.
  • Documents store a card on the link itself and draw it after the line (spec §13.3, "A reference's card").
  • Miky's model in his words: Widgets 2's project conversation, 15 Oct 14:03. "Exactly one file" and "old messages oddly is fine" come from the WID-2 session as written in the project description; I could not read them in his own words.
  • Not measured: how many sent messages hold a lone link that would turn into a row.
