A file: one whole record, or its fields?

Decision brief, 30 Oct 2026. It asks again a call you made on 29 Oct (brief "What a file is", A over C), because the fact that decided it turned out to be false. Initiative "Re-architecting Osnova protocol"; project "A load stays the same size as edits pile up: projects". About six minutes. A second, smaller question is at the end and is asked on its own.

The question. When people, apps and agents change the same file, does each save carry the whole file, every field and the text (A, chosen on 29 Oct)? Or does each change carry only the fields it touches, with the relay keeping each field in order (C)?

On this page: Why again · Today · What stays either way · The picture · Options · Four questions · Trade-offs · How others do it · Recommendation · The smaller question · Checked

Why this is asked again

The deciding fact was wrong. On 29 Oct A won because "an outside company holds a file's own state on upstream Buzz as it ships", while C "is ours alone". Checked on 30 Oct: upstream Buzz refuses every kind of event it does not know, and it knows none of the others Osnova needs: listings, who is on a file, an app's listing, Folders, projects, issues. So an outside company has to run our relay under A, exactly as under C. Two independent reviews found this. Your rule is that a premise found false after you decided means asking again.

Seen without that fact, what A really buys is relay code that Block writes and keeps working: the ordering, the current-and-history read, removal of a save. That is real, but it is a cost argument. And C has four advantages the 29 Oct page never set beside it: nothing is re-signed, a field change stays small, an app cannot wipe a field it does not know, and who changed which field is signed by that person.

Nothing irreversible has happened yet. No app writes a file this way; the only such files on production are the QA probe's. It becomes one-way when every project moves, the last step of the project.

Today

A file (an issue, a project, a Leaf page) is a starting record plus a pile of "set this field" changes, each signed by whoever made it. Each app adds the pile up, and for each field the newest clock wins. A text save carries a whole copy of the text. On 29 Oct the pile was 42 MB of text saves and 2.2 MB of other changes, and a cold Ship load downloaded 53 MB. Two saves crossing lose words silently: of 17 text saves within a minute of someone else's, 16 were QA-1, QA-2 or Claude.

What stays either way

Both reviews keep the core of what you decided, and so do both options below: the relay keeps each file's current state in order and refuses a save made on an out-of-date copy; everything names a file by its id; who is on a file stays beside it; lists stop growing with edits; search finds a file by its current words; shared types carry Osnova's name (osnova.project) and builders name their own and launch. Neither review offers git or Buzz's Projects-and-Issues screen as the file model: Buzz's issues cannot be edited, need a code repository, and are readable by the whole company.

The picture

Three options

A · A file is one record, saved whole chosen 29 Oct

What you see. Lists stay flat. A save made on an old copy is refused in every app and agent, and the app merges: different fields and blocks quietly, a block both people changed by asking. History shows whole versions, so "go back to Tuesday's version" is one step.

Outside company. Runs our relay. Reads one event and has the whole file. Writes the whole file back, and must keep every field it does not know: if it drops one, the HR app's "Salary band" on a candidate is gone from the current version until someone restores it.

What could go wrong. Every field change carries the whole text, to the relay and to everyone watching the Folder: Katerina's status flip on a 94 KB document is a 94 KB write. The largest file halves, from about 500 KB to 256 KB. The move re-signs about 1,500 events that name a project and deletes the old records, and undoing it is possible only while Estiva ID holds every author's key. Who changed which field is recovered by comparing versions; that is exact, but not signed by them. Upstream is reshaping the list and live reads right now, and our copy already differs from theirs in about ten places.

C · A file is its fields, each kept in order recommended

What you see. Lists stay flat. Katerina changing the status while Claude writes never collide. Two people editing the same text are handled exactly as in A: the second save is refused and merged. History is who changed what, as Ship's Activity shows today; going back to Tuesday is worked out from it.

Outside company. Runs our relay, as in A. Writes only what it changes, naming the change it follows for that field, and reads current values from the relay. It cannot wipe a field it does not know, because it never writes it.

What could go wrong. It is our relay code and our standard: an order per file and per field, a bulk read of current values, search over them. We maintain it, not Block. A change that names no previous change must be refused, or it races as today. Several fields changed together must be refused together, or a half-applied change shows. The artifact record and its SPEC section, one day old, are rewritten. Block's agent settings stay artifacts, so our relay carries both.

Do less · Lists read current values; nothing is refused

What you see. Lists stay flat. Everything else is today: two text saves crossing, the newest clock wins, and Leaf's and Ship's notice is the only warning.

Outside company. Today's events, plus a read of current values from our relay.

What could go wrong. It fixes the load and nothing else. Agents are who collide (16 of 17 crossings), so as more agents edit, more words are lost without anyone seeing it.

How others do it

  • Linear: one server orders every change, field by field; the newest value per field wins. The closest to C.
  • Salesforce, HubSpot, Jira: an update sends only the fields it changes, and Jira's history is a list of field changes. Whole-record replace exists, but integrations are told to send only what they change, because whole writes wipe what another integration set.
  • Notion: edits are small operations on one block or one property, not a whole page.
  • Buzz (NIP-AR): whole saves, A's shape. Used upstream only for agent settings so far; Block's own proposal to make tasks and projects artifacts (#7771) was closed unmerged on 21 Sep, and Buzz's Projects screen uses git-forge issues instead.

Recommendation

C: a file is its fields, each kept in order by the relay, and the text is one field saved whole. Osnova's point is many apps from many companies working on the same shared files, an HR app adding its fields to a candidate that a tracker from another company also edits. What those apps share is the field, not the whole file. C makes the field the unit that is signed, ordered and protected: an app cannot wipe what it does not know, a status flip cannot collide with someone's writing, and "Katerina set Stage to Offer" is a fact she signed. The text keeps A's rule, which is where whole saves fit. And if C turns out wrong, it can still be turned back.

This reverses what I recommended on 29 Oct, and the reason is the corrected fact, not new taste. What A still has is Block writing and maintaining the ordering code. For a small team that is worth a lot, and it is a cost argument: if you weigh it above the four points, A stays defensible, and four changes then come before projects move (a reference that names the file's home, so two companies' ids cannot collide; aliases instead of converting a type in place; the relay never refusing by type, below; and talking to Block about the list and live reads they are building now).

If C: the artifact record is superseded in part; SPEC §6.13 is rewritten; the relay's artifact support stays for Buzz's agent settings only; search reads current values instead of current saves; and the move shrinks to adding the order rule, with nothing re-signed. If A: the record's premise is corrected and the four changes are asked at their tickets.

The smaller question, asked on its own

When apps declare their types to the relay, may a declaration ever make the relay refuse a save, or only change how files are found and ranked?

Today. The search record waiting on your merge (estiva-docs#354) has the relay keep a table per type of which fields are words, with the project's built in, and refuse a project save that has text but does not say its format. On 26 Oct you turned down "the relay is the workspace's database, refusing writes that do not fit a type" because two companies' relays in a shared Folder would disagree, one schema bug would break every app, and a new kind of property would wait for a relay release.

  • Find and rank, never refuse by type recommended. "A save with text says its format" holds for every type alike, a rule of the envelope. A declaration the relay lacks or gets wrong only makes search worse. #354 changes one sentence before you merge it.
  • Keep #354 as written. Projects are refused today; whether later declarations may refuse is decided in that project. It leaves the door open to the 26 Oct rejected shape, one ticket at a time.
  • Do less: never refuse for search's sake. Unlabelled text is simply not found. An app that forgets the label learns it only when search misses.

  • Upstream already searches only current artifact saves: buzz-search/src/query.rs, "Search is a current-state surface; old artifact snapshots cannot match". The 29 Oct record says it has none.
  • Block #7771 (tasks and projects as artifacts) closed unmerged 21 Sep; #8522 (sync) and #8523 (incremental reads) open. NIP-AR: identity (community, d); "Editors MUST preserve unfamiliar fields … or decline the edit".
