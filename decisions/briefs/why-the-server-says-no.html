Why the server says no

Two protocol questions found while reviewing “Only you can set your following…” (the moves in Peek, Ship, Leaf and the agent). They are independent: either can be answered without the other. About five minutes.

1. How an app learns why a change was refused

When the server refuses a change, such as moving a topic to another team, should it say why in a short code every app can read, or only in an English sentence?

Today

Katerina moves a topic out of a team that is archived. The server says no with a sentence: “team 31afb7af is archived; its list does not change”. Peek looks for the word “archived” in that sentence and tells her, in Peek’s words, “Nothing was moved: one of the Folders is archived.” Ship, Leaf and the agent do the same, through one shared helper that matches words. The SPEC promises “a reason” but never says which sentences.

Why it reaches beyond this ticket

Every refusal any app explains goes through this: moves today, and later anything the server checks for a person. An outside company that runs its own server cannot know which sentences to send, so our apps tell its people “Nothing was moved. Try again.”, and trying again never works. An outside app has to copy our word list. Some refusals already read wrong in our own apps: a topic that may go only to its home team gets “Try again”, which cannot succeed.

Two-way door. A code can be added beside the sentence. Old apps keep reading the sentence, and nothing stored on the server changes. Undoing it later means apps go back to reading words.

The picture

Options

A. A short code before the sentence. The SPEC lists a handful of reasons, such as archived, not a member, changed since you looked, not its home team, leaves only by moving. The server puts one in front of its sentence. Katerina sees the same message as today, and a topic that can only go home says so instead of “Try again”. An outside company sends the codes from its own server and gets the right messages in our apps for free. What could go wrong: the list grows with every new rule, and someone has to keep it tidy. An app that meets a code it does not know falls back to “Nothing was moved.”

B. Name the exact sentences in the SPEC. Nothing new on the wire: the English becomes the contract. An outside server must send our sentences word for word. What could go wrong: rewording a sentence for clarity becomes a protocol change, and translating one breaks every app.

C. Leave it (do less). Our apps keep matching words. An outside server gets the generic “Nothing was moved. Try again.” for every refusal. What could go wrong: the wrong advice stays, and each new refusal adds another word to match.

How others do it

Nostr itself already does half of this: a refusal starts with a fixed word (invalid:, restricted:, rate-limited:), then free text. Slack’s API answers "error": "channel_not_found", and Matrix answers errcode: M_FORBIDDEN plus a sentence. Each of them separates a code apps read from words people read.

Recommendation: A. It is the shape Nostr and every API we would compare with already use. A code is what lets an outside server work with our apps, and it lets each app say the right thing, “this can only go to its home team” included. The sentence stays for people reading logs.

2. A team that can be archived two ways

Should a team have one way of being archived, or keep two that do different things?

Today

When Miky archives a team in Peek or Ship, the app writes the team’s “archived” field, the same way it archives a project or a page. Apps read it and grey the team out, and as of this ticket the server keeps the team’s topics where they are. There is a second way, from Nostr’s groups standard: an “archived” flag on the group’s own settings. When that is set, the server refuses every write in the team, its chat included. Our apps never set it, and only Peek’s conversation list reads it, to hide the channel.

Why it reaches beyond this ticket

An outside company sees two events both called “archived” on a team. One keeps its topics and still lets people talk. The other freezes the whole team, which is the option the accepted record “an archived team’s list is kept by the server” turned down, because whether people can still talk in an archived team waits for the Folders rework. Any Nostr groups client can set the second flag today, and our apps would mostly not show that the team is frozen.

Two-way door. Refusing the groups flag on a team can be lifted later. A team already frozen by it can be unfrozen by its owner.

Options

A. One way: the field. The server refuses the groups flag on a team, as it already does for the Company team, and the SPEC says a team is archived only by its field. What could go wrong: an outside groups client that archives a team gets a refusal and must use the field. Direct messages are not teams and keep their own archive.

B. One meaning, both ways. The server and every app treat either as the same archive: topics kept, chat open. What could go wrong: the groups flag would then mean something weaker than it does in every other Nostr groups server, which is confusing for anyone who knows the standard.

C. Keep both (do less). The SPEC says what each does: the field keeps the topics, the flag freezes everything. What could go wrong: a frozen team looks normal in our apps until someone tries to write.

Recommendation: A. A team is a file in our protocol, and files are archived by their field. One switch with one meaning is what an outside company can follow. It keeps the call you already made: archiving keeps the topics and leaves talking for the Folders rework.

Checked

  • Apps read the reason by matching words: interop 0.74.1 readMoveRefusal matches archived, only the team's members|not a channel member, does not list|lists none of|listed by one team, and falls back to a generic reason.
  • The home and remove refusals fall to the generic “Try again”: their texts (“a topic on no team's list goes first to its home…”, “a topic leaves a team only by moving…”, from buzz#47) match none of those patterns.
  • The SPEC names no refusal sentence for moves. The draft SPEC change in estiva-docs#379 quotes one, invalid: channel is archived, which would be replaced by A.
  • The groups “archived” flag freezes every write at the server (ingest answers invalid: channel is archived; buzz#47 notes). The server already refuses it on the Company team (SPEC §3.4).
  • Our apps never write the groups flag. Peek reads it only in its conversation list (src/nostr/dms.ts), to hide an archived channel.
  • Not checked: whether any team on production carries the groups flag today.
