A file's id and its link

When an app makes a file whose id is not one of our usual random ids, what link should that file get, so that it opens the same file in Peek, Ship and Leaf?

Today

Every file Peek, Ship and Leaf make gets a random id (a uuid). Its link is the title then the id: ship.estiva.app/issue/fix-login-3f0c1a52-…. You can swap the host for Leaf or Peek and it opens the same issue; pasted into a conversation it draws as the issue. You decided that on 20 Oct ("One file, one address, any app's host").

The protocol lets another app pick its own ids. Our main document says a file's id is a uuid; the shorter rule an outside company reads first (the file standard) only says it should be one. The link tests written this week tried thousands of made-up ids and found that for an id that is not a lowercase uuid, each app answers differently: Peek writes a long link with the whole address in it, Ship would write a short link that opens nothing, Leaf falls back to its old coded link. Production today has no such file (all 1,700+ files checked on 20 Nov).

Why it reaches beyond this ticket

It sets what any company building on the protocol may use as an id, and what link every app owes such a file. Today it is cheap either way. Once outside apps publish files with their own ids, or people paste their links into messages, the rule can only be loosened, never tightened: messages keep the links they were written with.

The picture

Options

B · A file's id is always a lowercase uuid, and the relay says so when an app tries another.

You and Katerina see nothing change: every file keeps one short, readable link. An outside company importing its tracker keeps "PROJ-123" as a field on the file (its title or a reference), not as the id. Its app learns the rule the first time it saves, from the relay's answer, instead of finding later that its links open nothing.

What could go wrong: a generic Nostr client that writes our file kinds with its own ids is refused. App settings and app listings are not files and keep their own ids (the census found ids like that only there).

A · Any id works, and every app writes and reads the long link for one that is not a uuid.

You see nothing change. An outside company can keep its own ids as the file's id. Every app, theirs included, must write and read two link shapes: the short one, and a long one carrying the whole address (Peek's today). Pasted into a message, the long link is ugly but works.

What could go wrong: two shapes forever, and each new app has to get the second one right; the week's tests found three apps getting it wrong three ways.

C · Do less: leave the rule as it is.

Nothing to build. The day an outside app uses its own ids, its links open in some apps and not others, and a pasted one may stay a plain link.

How others do it

  • Linear, Notion, Google Docs: the id in a link is always one the system made; a person's own code ("PROJ-123") is a field shown beside it.
  • Nostr itself lets an id be any text; that is why the file standard only says "should". The stricter rule would be ours, for our file kinds only.

Recommendation

B. One id rule gives every file one link that works in every app, which is what "one file, one address, any app's host" promised; our main document already says a file's id is a uuid, so this makes the file standard say the same and lets the relay tell an app at save rather than its people finding dead links later. It is also the reversible one: if an outside company needs its own ids, we can open the door to A then; closing it after links exist is not possible. The product reviewer on this ticket leaned A, for the outside company keeping its ids; I think a field carries that better than the id.

Checked

  • No file with a non-uuid id on production: every file kind read as the agent, 20 Nov (ids that are not uuids exist only on app settings and one app listing).
  • Main document requires a uuid id for a bare file and a document; the file standard says "should".
  • Each app's answer for such an id: from this week's tests and the fixes merged today in Peek, Ship and Leaf.
  • Not checked: whether any generic Nostr client writes our file kinds today (none seen on our relay).
