What an edit says about a message's files

A brief for Miky · 26 Oct 2026 · from "Editing can take every file off a message" (Peek moves onto the shared box) · you decided on 26 Oct that it must be possible; this is how

The question

When someone edits a message, should the edit always list the files the message keeps, or say something about files only when they change?

Today

When you edit a comment you can change its words, add a file, or take one of two files off. An edit says nothing about files unless they changed. When it does list files, that list replaces the old one.

Because an edit that says nothing means "files unchanged", no edit can say "no files". So Peek, Ship and Leaf all refuse to take off a message's last file. On 26 October you decided that this must be possible (your option C on PEEKM-4). What is left to decide is how an edit says it, and that sets what every edit means.

One thing we found while checking: Buzz's own desktop app, the upstream of our relay, reads edits the opposite way. There, an edit always lists every file, and an edit that lists none means "no files". So when someone fixes a typo in Peek today, Buzz desktop shows that message with no files. Buzz hit the same problem with mentions and solved it with a mark on the edit that says "this list is complete".

Why it reaches beyond this ticket

  • It is the edit rule for every app and every company. Anyone who shows an edited message has to know which files it has now. That includes an outside company's app, the agent, and the History panel you approved today (every version openable).
  • Part of it is a one-way door. What the mark means, or what an edit with no list means, is fixed once such edits are on the relay, and every reader has to honour it for good. How often apps write the mark can change later, so that part is two-way.

The picture

Options

A · Every edit is a whole version (recommended)

What you see: you take the last file off a comment in Peek, and Ship, Leaf and the agent show it with no files. When Katerina fixes a typo, her edit lists her two files again. Nothing on screen tells you this.

An outside company reads one rule: the files are the list on the newest edit that carries the mark. That is the same idea Buzz already uses for mentions. Buzz desktop reads every new edit from our apps correctly with no change, because each one lists its files.

What could go wrong: every edit names its files again, and the relay checks that each one is still stored. Today nothing removes a stored file, but if deleting a file is built later, fixing a typo in a message that pointed to a deleted file would be refused until the file is taken off. An app that writes no mark changes nothing about files, which is today's behaviour, so a simple or old writer cannot wipe files by accident.

B · Take Buzz's rule as it is

What you see: the same as A in Peek, Ship and Leaf. But 4 comments on production would show their files gone the moment readers switch rules: 3 of Katerina's (14 Sep, and two from 7 Oct) and one test comment. Bringing them back takes a new edit that only Katerina can sign.

An outside company gets the simplest rule, the same as upstream Buzz, with no mark.

What could go wrong: a forgotten list now means "no files". A tab still open from before the update, the agent's command line until it is rebuilt, or an outside builder who is new to Nostr writes a typo fix, and every file disappears from that message for everyone. The files are still stored and can be put back, but people see them vanish.

C · Do less: mark only the edit that takes the last file off

What you see: the same as A in our three apps.

An outside company reads the same rule as in A. Our typo fixes keep dropping files in Buzz desktop. An edit is not a whole version, so the History panel has to look back through earlier edits to show a version's files.

What could go wrong: very little. It is A's reader with fewer marks written, so moving to A later changes only what apps write.

How others do it

  • Buzz desktop (our upstream): every edit lists its files, and no list means no files. For mentions, where old edits existed, it added a "this list is complete" mark instead. That second case is ours.
  • Matrix: an edit carries the message's whole new content, never a patch. Every edit is a whole version, as in A.
  • Nostr's file tags (NIP-92) define no edits, and NIP-C7 chat apps never read edits at all, so they keep showing the original files whatever we choose.

Recommendation

A: every edit lists the files the message keeps and says its list is complete. Each edit then stands alone as a version, which is what the History panel you approved today will open. Upstream Buzz reads our new edits correctly, and an outside company meets the same "complete list" rule Buzz already uses for mentions. Unlike B, an app that forgets the mark changes nothing, so no simple or stale writer can make files vanish, and Katerina's old comments keep theirs. C would be fine as a first stage, but it leaves our typo fixes dropping files in Buzz desktop. Writing the mark on every edit costs little.

Checked

  • "An edit with no files means unchanged; emptying is not expressible": Specification §6.8, on estiva-docs main. The fold is the same in the shared library (foldAttachments, @estiva-app/conversation on main).
  • All three apps refuse taking off the last file: Peek ConversationBox.tsx:468, Ship ConversationBox.tsx:166, Leaf CommentsColumn.tsx:251, each on main.
  • Buzz desktop's rule and its mentions mark: desktop/src/features/messages/lib/applyEditTagOverlay.mjs and buzz:mention-snapshot in events.rs, on buzz nfb-demo-kinds.
  • The relay accepts a separate mark tag on an edit with no relay change. It refuses a new field inside a file tag, and a file tag with no file: validate_imeta_tags, buzz handlers/imeta.rs.
  • Production, read as the agent on 26 Oct, Folders it can read: 177 edits on 153 messages, 54 of them listing files. Under A or C, no message reads differently. Under B, 4 lose their files: 3 of Katerina's comments, 1 QA-1 test comment.
  • Not checked: Folders the agent cannot read. A private Folder could hold more messages that B would empty.
