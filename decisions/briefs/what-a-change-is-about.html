What a change is about

For Miky. Protocol only; asked on its own. About five minutes.

When an app changes a file (its status, its title, who is on it, which files a topic lists), how does the change say which file it changed, so that "what changed on this file" never picks up a change that only names it?

Today

  • Every change names the file it changes by the file's long address: its type number, its creator's key and its id. Ship ignores a change without one.
  • Since 29 Oct a file can also be named by its id alone, in two ways: "about it", which a comment uses for the file it is on, and "names it", which a mention, a Folder's listing and a card use. You decided the pair on the brief "Pointing at a file". That record files "who is on a file" under "names it".
  • This morning you decided that every later change names its file by its id (the brief "Types and Changes"). Which of the two ways it uses was never asked. The projects stage's plan puts "names it" on every project change, beside the long address, and has the relay refuse a change whose two disagree.
  • This stage writes "Widgets lists build 1" as a change on the Widgets topic that names build 1 the "names it" way, as a Folder's listing does.

Why it reaches beyond this stage

Every app, and every outside company on our relay, asks two questions about a file: what changed on it, to show it as it is now, and what points at it: the topics and Folders that list it and the messages that link it. The tag a change uses for its own file is the answer to the first question for every type: ours, a new base type, a builder's acme.candidate.

If "names it" means both, the two questions blur. Asking what changed on build 1 also returns Widgets' entry, so build 1 shows a field that belongs to Widgets, and the projects stage's check refuses Widgets' entry outright, because its two names disagree. Any change that names a second file hits the same problem: a move names the new parent, and an outside company's "blocked by", "duplicate of" or "related to" each name another file.

Two-way today, one-way in about three weeks. None of the 6,658 changes on production carries either id tag (30 Oct, read as QA-1). From the projects switch on, every project change carries the tag, and every reader then reads it with that meaning for good. A later change of mind means readers handle both meanings for every change written in between.

Options

A · A change is "about" its file, as a comment is recommended

You see
Nothing changes on screen. Widgets lists build 1; build 1 says "Topics: Widgets"; build 1's status and history show only build 1's own changes.
Outside company
One rule for everything: "about it" is the file the event is about (a comment, a change, who is on it) and "names it" is any other file it points at (a mention, a listing, a move's new parent, its own "blocked by"). Asking "about build 1" returns its comments and its changes together, a feed, unless it names which kind it wants.
Locks in
Every change from the projects switch on carries "about it". The 29 Oct record's line putting "who is on a file" under "names it" is replaced, and the projects stage's plan changes by one tag before anything is built.
Could go wrong
An app that asks "about build 1" expecting only comments now also gets changes; no app asks yet. Nostr's own comment standard reads the capital tag as a comment's root; a change isn't a comment kind, so no comment reader sees it, and we offer the pair upstream as our convention, as decided. Until the switch, every change also carries the long address, because Ship ignores a change without one.

B · A change keeps "names it"; a topic's list gets its own tag

You see
The same screens as A.
Outside company
Learns that a Folder lists a file in "names it" but a topic lists one in a third tag, and that "about" is the capital tag for a comment and the small one for a change. Its own "blocked by" needs a letter of its own too, or it hits the clash.
Locks in
A new letter for each relation that a change names, with Nostr's single letters as the budget. The 29 Oct line "anything that mentions or lists a file names it" is broken for topics.
Could go wrong
"What points at build 1" quietly misses its topics, so a future Linked-from or delete warning that asks one question shows an incomplete answer.

C · Do less: a change names its file only by its long address

You see
The same screens as A.
Outside company
Learns two ways to name one file: by id for comments, mentions, listings, cards and unread, and by the long address for changes. To ask what changed on a listed file it must first fetch that file's first record to learn its type and creator, so a topic of 30 files takes two round trips instead of one.
Locks in
Nothing new on the wire, and adding the id later is additive, so it's the easiest to undo. It reverses this morning's "every later change names its file by its id".
Could go wrong
An app that has only a file's id, from a listing, a chip or a link, can't ask what changed until it has found the file's first record. One that skips that step reads no changes and shows the file as if it were new.

How others do it

  • Linear, Jira: a history entry is keyed by the issue it changed; a relation such as "blocks" is a separate field naming the other issue. What was changed and what is referenced are never the same field.
  • AT Protocol: a record has its own key, and a like or repost names what it is about in a separate subject. The same split as A.
  • Nostr comments (NIP-22): capital for the root a comment belongs to, small for what it replies to. It has no rule for changes, because Nostr files usually replace themselves whole.

Recommendation

A. A change is about the file it changes, the way a comment is about the file it sits on, so it uses the same "about it" tag; everything a change merely points at, such as a listed file, a new parent or a builder's "blocked by", uses "names it". That gives an outside company one rule with no exceptions, keeps "what points at build 1" complete, and asks what changed on 30 files in one request. C is cheaper to undo, but it makes changes the one place a file is named differently, which is exactly what the id was introduced to end. Nothing on the wire carries either meaning yet, so A costs one tag in the projects stage's SPEC issue, which isn't written.
