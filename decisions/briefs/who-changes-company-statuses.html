Decision brief · project "Each company sets its own statuses" · 30 Oct 2026 · for Miky

Who changes a company's statuses

You decided that only the workspace's owners and admins change a company's statuses. What stops anyone else, and who checks it: every app, or the relay?

Today

Statuses are written in Ship's code. Nobody can change them. On 30 Oct you decided that each company keeps its own statuses in one file per type (one for projects, one for issues) in its Company Folder. Only the workspace's owners and admins change that file. A change from anyone else, including an app's key, should change nothing anyone sees. The record left one thing to this project: what enforces that.

Two facts shape the answer:

  • Every member may write in the Company Folder. That is its rule today, so this file would be the first thing in it that only some people may change.
  • Every member can already see who is an admin. The relay publishes its member list with each person's role, and every app reads that list for its @ menu. Production on 30 Oct: 1 owner, 3 admins, 10 members.

Why it reaches beyond this project

This is the first company setting that only admins may change, so the answer is the rule for every setting that follows: labels, priorities, a company's own columns, and settings an outside company's apps keep. It decides whether "only admins" is something every app has to get right, or something the relay guarantees once, for every app.

Mostly one-way. Whatever the files carry about who may write them stays on the relay, and every app learns to read it. Changing the rule later means re-checking every settings file already written. A rule that only lives in apps (option A) is cheaper to change, but the changes it ignored stay on the relay for good.

Options

A · Do less: every app ignores changes from non-admins

The relay stores anyone's change, as it does today. Each app checks the member list and draws only what owners and admins wrote.

  • What you and Katerina see. If Katerina changes the statuses through some other app, nothing changes in Ship, Peek or Leaf. An app that forgot the check would show her change.
  • An outside company builds the check into each of its apps and gets it right in each one.
  • What could go wrong.
    • The relay keeps the changes in order, and each change names the one before it. An admin's next change then follows a change every app ignores, so every app needs the same rule for skipping over it.
    • The member list holds only today's roles. When an admin is demoted, apps either drop everything they ever wrote, so the statuses go back, or need the old roles, which nobody keeps.
    • Finding the file by an id made from its type does not work: any member can create a file with that id first, and the relay then refuses the admins' one. Apps would have to search for it instead, and skip files that members made.

B · The relay refuses non-admins' changes to a statuses file

The relay knows the statuses type and takes a change to it only from an owner or an admin.

  • What you and Katerina see. If Katerina tries to change the statuses, the relay says no and her app tells her why. Every app shows the same thing.
  • An outside company gets the guarantee for our statuses, but each setting of its own needs a relay release.
  • What could go wrong. This goes against a type's declaration changes how files are found, never what is accepted (Accepted 30 Oct), which says the relay never refuses a save because of its type. So it means superseding that record, and every new settings type waits for relay code.

C · A file can say "only admins write here", and the relay keeps to it Recommended

Any file, of any type, can be created with a mark saying only the workspace's owners and admins write it. The relay creates a marked file only for an owner or an admin, then takes changes to it only from them. The company's statuses file is created with the mark. Apps find it by its type and the mark, in the Company Folder, and skip any copy without the mark.

  • What you and Katerina see. The same as B: if Katerina tries to change the statuses, the relay says no, and every app shows the same statuses.
  • An outside company gets "only admins write here" for any settings file of its own, with no relay release and no per-app checks. Upstream Buzz has no such mark unless we propose it.
  • What it locks in. A new right that every Estiva relay enforces, written on the file's first record for good. Later it can grow into other groups, such as "only this team", without changing the shape.
  • What could go wrong.
    • A member can still create an unmarked file of the same type. Apps skip it because it has no mark, so it changes nothing anyone sees.
    • Two admins could each create a marked file; the SPEC says the oldest one counts.
    • A demoted admin's earlier changes stand, because the relay checked them when they were written.
    • The relay rule is new work, and our apps read the file only once it exists, which is after the admin editor's project.

How others do it

  • Matrix: each room says which power level may send each kind of room setting, and every server enforces it. This is C's shape, kept per room. (From memory, not checked today.)
  • Notion: changing a database's properties, such as a select's options, takes edit rights on that database. That is a right carried by the object itself, as in C. (From memory, not checked today.)
  • Jira: in a team-managed space, the space's admins edit its statuses. Linear sets project statuses for the whole workspace; we have not confirmed who may edit them. Both enforce it on their own server, so only one app ever has to get it right.

Recommendation

C: a file can say "only admins write here", and the relay keeps to it. "Only admins change the company's statuses" is a promise about the company's data, so it should hold whichever app someone uses, including one we did not build. The relay can keep that promise once, with one rule that is the same for every type, which is exactly the kind of refusal the Accepted record allows. A spreads the promise across every app and leaves changes in the file that every app has to agree to skip. B keeps it, but only for our type, and against a record you accepted today. C also gives an outside company the same guarantee for any setting of its own.

Checked

  • Every member can read who is an admin. The relay's member list carries each member's role, in our relay and in upstream Buzz (crates/buzz-db/src/store/relay_members.rs, ["member", key, role]). The agent, a member, read it on production on 30 Oct: 1 owner, 3 admins, 10 members. The shared people list reads the same list (packages/conversation/src/people.ts). The relay's separate HTTP member read is admins-only (crates/buzz-relay/src/api/members.rs), but no option needs it. The pre-review said "the list names members only", and that is wrong.
  • Taking a file's id first. SPEC "One id, one file": the relay refuses a new file whose id is already held, by any author (protocol/SPEC.md ~1829, checked on production 30 Oct). So any file found by an id made from its type can be taken first by any member. C avoids this by finding the file by its mark, not by such an id.
  • The relay never refuses by type. Record a-types-declaration-changes-how-files-are-found-never-what-is-accepted, Decision: "The relay never refuses a save because of its type", while "the right to write there" still refuses (estiva-docs origin/main).
  • Any member writes in the Company Folder, and "admins" means the relay roster's owners and admins: record a-companys-statuses-are-its-own-layer-of-a-types-properties (estiva-docs#358, waiting on your merge).
  • Worth knowing. On production the agent's key is one of the 3 admins, so under B or C it could change the statuses.
  • Not checked: Matrix's exact rule, and who may edit Linear's statuses.
