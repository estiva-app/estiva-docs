What a file is

Decision brief, version 3, 29 Oct 2026. It replaces version 2 from the same morning, after a fresh product and protocol review found that "adopt artifacts as they are" cannot be built as drawn, and that several of its facts were wrong. Initiative "Peek, Ship and Leaf are fast", step 3. About twelve minutes; the tables can be skimmed.

The question. For every app and every company on Osnova, what is a file? A pile of "set this field" changes that each app adds up, with the newest clock winning? Or a record whose current version the relay keeps, refusing any save made on an out-of-date copy?

Two calls come first, because every option that changes the file needs them: D1, one reference that names a file everywhere, and D2, membership kept beside the file. The main call and D3–D6 follow.

Today

A file (an issue, a project, a Leaf page) is a starting record plus a growing pile of changes, each one "set this field to this value", signed by whoever made it. Every app reads the whole pile and adds it up. For each field the newest change wins, by the clock of the device that made it. A text save is one such change and carries a whole copy of the text. Who is on a file is one change per person ("Katerina: on this file").

On production on 29 Oct the pile holds 2,732 text saves weighing 42.0 MB and 3,649 other changes weighing 2.2 MB, across 1,171 files. It has grown 8–17 MB a week this month. A cold Ship load downloads 53 MB, and 43.8 MB of that is this pile. What a list actually needs is much smaller: the newest value of every field is 1.5 MB, and every file's newest text is another 5.1 MB.

Already decided. On 26 Oct you chose (brief "Files, Types, History") that the relay keeps a small summary of each file's current state and signs it itself, that the text moves to an event of its own where the last save wins, and that every shared type gets a number of its own. None of it is built, and the SPEC does not describe it yet. On 29 Oct you added: a shared type carries the protocol's name (osnova.issue, singular); a builder names its own types and launches; a type that is standardised later converts; Leaf tabs are sections of one document; old chips and references are migrated or dropped, with no compatibility layer; and search must work before any type moves.

The new fact behind v2 still holds. Upstream Buzz added artifacts on 28 Sep: an editable record in one channel (for us, a Folder), where each save is a whole copy that names the save it was made on. The relay refuses a save made on an out-of-date copy. Our relay carries artifacts behind a switch that is off. Upstream uses them only for agent settings, and the standard is a draft.

Why it reaches beyond this project

  • It sets what a file is for every app and every outside company. Ship, Leaf, Peek, the agent and anything a partner builds read and write files one way.
  • It sets who protects a person's words when two saves cross. That can be each app on its own, as Leaf and Ship do today, or the relay for every app and agent.
  • It sets how everything else names a file (comments, mentions, listings, unread state, pasted chips), and so whether a file can change type (D1).
  • It sets who orders a shared file's changes when two companies share a Folder.
  • Door: the 26 Oct shape, A and B are one-way. Each moves every file and needs a second migration to undo. C is close to two-way: it adds a rule the relay can stop enforcing, and old changes stay valid.

Four options

Baseline · the 26 Oct shape Accepted, not built

What you see. Lists of summaries, flat as edits pile up. Two saves crossing behave as today: the newest clock wins, and Leaf's and Ship's notice is the only warning.

Outside company. It needs our relay to add up changes and sign summaries. A plain relay works slowly, and upstream Buzz answers none of it.

What could go wrong. The relay's summary repeats every app's adding-up rules (which Folder a change counts in, who may take a person off), and the two must never disagree. Your naming call of 29 Oct means one kind of starting record carrying a type name, instead of a number per type. That is a change to this shape as well.

C · Field changes, ordered by the relay

What you see. Lists of current values, flat. Katerina changing the status while you edit the text never collide, because those are different fields. Two people editing the same text are protected: the second save is refused and the app is told. History stays the change list, as today.

Outside company. It writes field changes, each naming the one it follows, and our relay orders them. This is our own rule, offered as a standard of our own. Upstream Buzz relays answer none of it.

What could go wrong. It is new relay code: a head per file and field, a check on every change, a backfill from production, and a bulk "current values" read. Every app must say which change each one follows. A change that does not say so is either refused, which breaks plain Nostr clients, or races, which is today's behaviour. A database view ("candidates whose stage is Offer") needs an index of current values that we build ourselves. Linear works this way: one server orders every change, and the newest value per field wins.

A · Hybrid: the file's state is an artifact recommended

What you see. Lists of current saves, flat. A save made on an out-of-date copy is refused in every app and in the agent. Different fields merge without asking, and only the same text asks (D4). History lists whole versions. Who is on a file, comments, listings and unread state work as today, as their own events that name the file by one reference (D1, D2).

Outside company. The file's own state runs on upstream Buzz as it ships. Listings, membership rules and unread state are still ours, so a partner relay needs them too. "No Estiva code" (v2) was overstated. A builder writes acme.candidate, with filterable properties as tags, and asks nobody for a number.

What could go wrong. A status change from a list row must first fetch the whole save. An app that saves from the row without the text would write an empty text that the relay accepts as current: conformance tests guard this. A live feed can be narrowed by Folder, but not by type. A save sends no push, so an assignment needs its own notification. Upstream's standard is a month-old draft and may change. History weighs about a fifth more (53.5 MB instead of 44 MB), and only the History panel reads it.

B · A, with a number per type

The same for Miky and Katerina. A number would still let a relay that does not know artifacts narrow a live feed to issues, but such a relay cannot tell which save is current anyway. B costs our own variant of upstream's standard for good, and upstream relays refuse our files. Your 29 Oct call on names already points away from it. v2 claimed that converting is harder under B. It is not: B also names a file by its id, not its number.

Two people saving at once: what people meet

Leaf and Ship already warn you. When Katerina saves while your cursor is in the page, both apps show "Katerina saved a newer version. Load it (replaces your changes)." That gives you two choices, and both lose words. If you load hers, your typing is discarded. If you keep typing and leave, your save replaces her text. If your cursor is not in the page, her text replaces yours on screen without a word. The agent's edit-issue reads first and then writes with no check, so a save made in between is replaced. Peek edits no texts.

How often it bites, measured 29 Oct. Between Miky and Katerina: never the same field within a minute. There were 17 text saves within 60 s of another person's text save. Sixteen were QA-1 and QA-2 probes or Claude, and one was Katerina after her own Claude (13 Sep). Words were lost twice, both times in QA two-person probes. v2's "29 times" counted any field followed by a text save, test accounts included.

So the case is not today's pain. It is the case the notice already admits: the right moment, with a third choice missing. With C or A the relay refuses the out-of-date save in every app and agent, so the app can offer "keep both" instead of "lose one" (D4). That matters more as agents and automations edit beside people (Osnova's fourth question), and in a Folder two companies share. The 26 Oct shape leaves it to each app.

D1 · One reference that names a file everywhere big · asked first

Today a file is named by its type, its author and its id together, in comment roots (3,520 comments), mentions, Folder listings (723 listing changes), unread state, cards and block links. A pasted chip carries the same name, and it is pasted into 190 comments, 16 messages and 14 issue texts. An artifact has no author in its name. Converting a type (your 29 Oct call) also breaks any name that includes the type.

  • a · The file's id, in one marker that every event uses recommended. It is written into the SPEC and proposed upstream beside artifacts. Ids are already unique across every type and author (Accepted 3 Oct), so this works under every option.
  • b · Keep type, author and id. This works for the 26 Oct shape and for C, but it rules out A and B, and it rules out converting.
  • c · Name the file's first save (v2's pick). Removing that save, a pasted password or "delete this version", hides it everywhere, and the file then cannot be found. The first save also no longer says the type.

Recommend a. A file's name should hold only what never changes. Old chips and references are rewritten by the migration or left dead, as you decided. Comments, listings and unread state are rewritten; signed messages carrying a chip are republished or keep a dead chip, and the migration decides which.

D2 · Who is on a file stays beside it big · asked first

Today anyone may add a person to a file, only you can take yourself off, and a mention in a file's text adds the person without an unread. Each is one small change about one person. If the file became whole saves and its people were part of each save, every add would be a new version of the file, written by someone who needs to be able to edit it. A leave would be a save of the file by the person leaving. A live feed of "files I am on" would bring every edit of every one of them.

  • a · Beside the file: one small event per join, add or leave, naming the file by its reference recommended. Your three membership records stand word for word.
  • b · Inside the file's saves, as upstream's people tags. Adding someone becomes editing the file, and it collides with the people writing it.

Recommend a. Who follows a file is about the person, not the file. This is only a question under A and B. Under the 26 Oct shape and C, membership already is per-person changes.

Search, before any type moves

You made search a condition of the first stage. Today the relay searches messages, comments and profiles, and finds files by title only, not by their text. Upstream has no artifact search: its word search would match every old save as well as the current one, on raw data, and would miss titles.

  • What it searches: each file's current version only, meaning its title, its text-valued properties and its text.
  • How it matches: every word as a word start, as Accepted on 19 Oct.
  • Who sees a hit: only someone who can read the file's home.
  • Built as: the relay updates the index on every accepted save (A), on every newest value (C), or from the summary (the 26 Oct shape). This is ours to design and to propose upstream for A.
  • It is a Done-when leg of the first stage, not a later ticket.

Two companies sharing a Folder

The Accepted record (26 Oct): a shared Folder lives on both companies' relays, the host's relay runs it, and "every relay folds the same events into the same result". Nothing is built.

  • C and A both need the host to order. The partner's relay passes each change on to the host and waits for "accepted" or "out of date". When the host is down, partners cannot save shared files, which the record's "the host says yes or no" already implies. The exchange between relays must carry that order, as well as removals and redactions.
  • Under A, a host admin can remove a partner's save under upstream's rules, and removing the current save retires the file. The record says "the host can take a person out, not delete their words", so the exchange must limit this.
  • The 26 Oct shape keeps "every relay adds up the same", with clocks deciding.

Calls kept from v2, if A

  • 1 · A list reads current saves without their text: an option our relay adds and we propose upstream. Lists carry 1.5 MB instead of 6.6 MB, and a relay without the option refuses the request plainly. Still recommended.
  • 2 · Estiva ID limits which types an app or agent signs, as it limits kinds today. A key that signs directly bypasses it, as it does today. Limits are per type, not per field (see "What it overturns"). Still recommended.
  • 4 · Moving a file changes only where it is listed, for now. Upstream's move changes who reads, and keeps old versions readable only to the old Folder. It waits for the navigation rework's access call. Still recommended.
  • 5 · Names: decided 29 Oct. Shared types are osnova.issue, osnova.project, osnova.document, osnova.topic. Builders name their own types and launch. The prefix is permanent on the wire, so the protocol's name is final before the first file is written.
  • v2's call 3 (a comment names the first save) is replaced by D1.

Four smaller calls, after the main one

D3 · What Delete means

Today only the author (or the person whose agent made it) can delete, a delete hides the file's starting record, and its history stays readable. Upstream: anyone who may post in the home may delete or restore, and a delete is a save saying "deleted". Separately, the author or a Folder admin can remove one save for good.

Recommend: Delete is restorable, by anyone who may edit the file, and is shown with who did it. "Remove for good" is a separate action for admins, for a pasted password. This overturns "nobody may delete another person's work" and "deleting removes every save".

D4 · A save refused because someone saved first: what you see

Under C or A. Your call on the behaviour, and Katerina's on the look, from a Storybook prototype first.

Recommend: merge block by block, and ask only about a block both people changed. The alternatives are to keep theirs and offer "Your version" to copy back, or to build the live co-editing layer (Accepted for later) first.

D5 · Who reads a project

Today 24 of 34 projects are readable by everyone in the workspace. Their issues are readable only by their Folder. An artifact needs a home, and the home's members are its readers.

Recommend: a project's home is its Folder or team, Company by default, which matches the navigation direction. That makes the access brief's call ("Who leads, who reads") a little more urgent.

D6 · How a type converts

You decided that a standardised type converts. Upstream says an artifact's id and type never change, and its agent-settings standard depends on that.

Recommend: a "convert" save that changes the type and keeps the id, links, conversation and history. It is allowed only for types whose directory entry says what they convert to, so agent settings are never touched, and it is proposed upstream. If upstream refuses, we carry it as our rule. The alternative is a new file that names the one it replaces, with links pointing at the old one.

Osnova's four questions. One company across all its apps: A and C both answer "everything assigned to me" from current state. A asks one question across every type, while C needs our index. Builders integrating: A is a standard Block also runs, and C is ours alone. Cross-app actions and agents: in A and C an agent's out-of-date save is refused instead of silently undoing a person's, while the 26 Oct shape leaves that to each app. Intelligence: the same, plus versions an agent can diff.

Recommendation

A, as a hybrid: the file's own state is an upstream artifact named osnova.issue and so on, and membership, comments, listings, unread state and references are their own events, keyed on one reference to the file (D1 a, D2 a).

For the person. Leaf and Ship already tell you when someone saved first, but they can only offer to lose your words or theirs. With the relay refusing an out-of-date save in every app and agent, "keep both" becomes possible everywhere (D4). Lists stop growing with edits.

For the protocol. The relay owns identity, access and order; apps own meaning. A builder gets one shape for any type, the same as Block's, with no number to request. The pieces that stay ours (listings, membership, unread state, search) all hang on one reference that never changes.

C is the strong alternative. It is Linear's shape, it keeps per-field authority, and it is nearly two-way. It would be the better pick if upstream refuses our three proposals (the reference, leaving the text out, convert), because A would then be our own variant anyway. Ask Block before the first stage builds.

Cost does not tip it: A is the largest build. It is staged with one type end to end, search included.

Checked

  • Production, 29 Oct (read-only queries): the pile's size above. Who saved within 60 s of another person: Miky's and Katerina's keys never within a minute of each other; Miky and his Claude 22 times, never on the same field; the 17 close text pairs and the 2 lost texts as above. Chips pasted in 190 comments, 16 messages and 14 issue texts. The busiest file has 3 people added by membership changes.
  • Leaf and Ship: the notice and its copy in the shared editor (estiva-ui DocumentEditor), its "replaces your changes", and that a save names no version it was made on. The agent's edit-issue does not check between its read and its write. Peek has no text editor.
  • Relay: artifacts are behind a switch that is off. Upstream's delete and restore are allowed to anyone who may post in the home. Removing the current save retires the file. Search finds file titles, not text. The text limit is 256 KB (512 KB is the message frame). A Folder delete counts only today's four file kinds, so it would hide artifacts. No part of the 26 Oct summary is built. C's ordering needs a new table and a new read; the artifact machinery shows the pattern.
  • SPEC and records on origin/main: each row of "What it overturns", the membership rules, and projects being readable workspace-wide (24 of 34, measured 29 Sep).
  • Migration: CON-20 re-signed old events with their authors' own keys, exported from Estiva ID. Turning a field change into a whole save would put a version in someone's name that they never saved. So under A, each file's current state becomes its first save, and older changes stay readable as they are.
  • Not checked: whether Block would take the reference, the leave-out-text option or convert; whether production's search index would pick up artifacts as configured today.
