One file, one address, any app's host

A brief for Miky · 20 Oct 2026 · project "Leaf edits any file's text" · two questions, the second builds on the first

1. Should every Estiva app open every other app's address for a file, with only the host changed, either drawing the file itself or handing you to the app that owns it?

2. When someone pastes Leaf's address for a Ship issue into a message, should it draw as that issue (its chip, row or card, and a mention on the issue), the way Ship's own address does?

The moment

Today, 20 October, you rewrote a Ship issue in Leaf, took Ship's address for it, changed only the host and opened leaf.estiva.app/issue/b2d86f1f-…. Leaf showed Home. "The URL should be very much same in Ship and Leaf."

Today

  • You wrote this rule on 21 September, in the association RFC: "the path names the file; the host names the perspective". ship.estiva.app/project/x and peek.estiva.app/project/x are one file: Ship draws it as a project, Peek as a conversation, and an app with no view of a file hands you to the app that owns it. "A 404 or an empty page is not an option."
  • Peek and Ship already work this way. Peek opens any file word the apps declare (/project/, /issue/, /document/) on its file page; Ship hands /topic/ and /document/ to Peek and Leaf.
  • Leaf does not. It knows only its own /document/ and an internal /f/… form, and sends anything else to Home. That is what you hit.
  • The rule was never written as a decision record or into the protocol spec. It lives only in the RFC. So it binds nobody new, an outside company reading the spec would not know it, and the house rule is to ask before building on it.
  • Pasted links are a separate half the RFC left open. It says a reader may recognise any Estiva host on a file's path. Nothing built does. The spec says a reader must match the exact host an app declares, so today even peek.estiva.app/issue/… pasted in Ship is a plain link.

Why it reaches beyond this ticket

  • It is the rule every app and every outside company follows for what its addresses mean and what it owes another app's addresses. An outside company building an app needs to know: if my host gets /issue/…, must I answer it, and will my address for your file be recognised in a message?
  • Question 1 is close to one-way. A link is stored as the URL its author wrote (record "a link is stored as the URL a person wrote"). Once Leaf's address for an issue is in people's messages and pages, Leaf owes /issue/ for good.
  • Question 2 is one-way for messages already sent. Whether a message counts as mentioning the issue is decided once, when it is sent. A Leaf address pasted before readers recognise it never lists that message on the issue. Drawing can change later; the mentions cannot.

Question 1 — does every app answer every app's address?

1A. Yes, for every app (your 21 Sep rule, made binding)

Any Estiva app opens any declared file path. It draws the file if it has a view of it (Leaf: a Ship issue as a page; Peek: its conversation) and otherwise hands you to the owning app (Leaf on /topic/ says "Open in Peek"). The type word is the owner's (issue, project, topic, document) on every host.

You see: change the host, keep the path, and you are on the same file in the other app. An outside company: declares its words once, and every Estiva host answers them; it must answer theirs too. Locks in: one shared vocabulary of file words, with a collision check when an app publishes.

1B. Only Leaf takes Ship's paths

Leaf adds /issue/ and /project/ and stops there. You see: this one swap works; leaf.estiva.app/topic/… still shows Home. An outside company: no rule to follow; each pair of apps agrees on its own. Peek and Ship already do more than this.

1C. Each app owns its paths; others send you to the owner

leaf.estiva.app/issue/… redirects to ship.estiva.app/issue/…. You see: the swap lands in Ship, not in Leaf's editor, which is the opposite of what you wanted today. It would also undo what Peek and Ship do now.

Recommendation: 1A. It is the shape you chose on 21 September, two apps already follow it, and it is the only one in which an address means the same file to every app, including an outside company's. The host then says only whose view you are in, which is what "the URL should be very much same" asks for.

Question 2 — is a pasted Leaf address recognised as the file?

The moment: you rewrite an issue in Leaf, copy the address bar, leaf.estiva.app/issue/plan-…, and paste it into a Peek conversation for Katerina.

2A. Any Estiva app's host on a declared file path is that file

Readers recognise a file path on the host of any Estiva app, not only the owner's. One added line keeps lookalikes out: an app declares addresses only on its own host. You and Katerina see: Ship's, Peek's and Leaf's address for one issue all draw as the same chip, row or card, and each opens in the app it names. An outside company: declares its file words once, and every Estiva host's address for its files is recognised, with no change to anyone else's app entry. Locks in: the 21 Sep rule carried through to messages.

2B. Each app lists the other apps' addresses it serves

Leaf's app entry adds "/issue/ and /project/ on my host are Ship's issue and project". You see: the same as 2A, for Ship's files only. An outside company: every app must re-list every other app's words and republish whenever one is added; a new app's files are never recognised on Leaf's host until Leaf does. It also blurs which app owns a type, which the protocol keeps separate.

2C. Only the owner's address is recognised

Leaf answers /issue/ (question 1) but its Copy link gives ship.estiva.app/issue/…. You see: an address bar you cannot simply copy and share; a Leaf address pasted by hand stays raw text in Peek while Ship's draws the issue. The two "same" addresses behave differently in a message.

Recommendation: 2A. It is your 21 September rule finished: the path names the file wherever it is pasted, and the host only says whose view it opens in. It is the one shape in which an outside company declares its files once and every Estiva app's address for them works. 2B gets the same screen for Ship today but makes every app list every other app's types, which no outside company would accept. Build order, not shape: until the shared reader recognises Leaf's host in all three apps, Leaf keeps copying the address it copies today, because a message sent before that never counts as a mention.

How others do it

  • Google Workspace: one file id; docs.google.com/…/d/<id> and drive.google.com/file/d/<id> are two views of one file, and Chat recognises both. That is 1A + 2A, from one company that controls every host.
  • Bluesky (AT Protocol): the identity is the at:// address; each app's web URL is its own view, and other apps do not recognise it. Closer to 2C, which is why links between Bluesky apps are often plain.
  • Notion, Linear: one app, one host; the question does not come up.

Checked

  • The 21 Sep rule: association RFC §7.7, "The path is the same on every host", marked "Added 2026-09-21 (Miky)" (estiva-docs, origin/main).
  • Not in the spec or any decision record: searched spec and decisions/ on origin/main.
  • Peek opens any declared file word: one file route, words read from the app entries (Peek App.tsx, FOL-39). Ship hands others' words off (Ship router.ts, handoff.ts, PRO-22). Read in code; on production, checked for Leaf only.
  • Leaf shows Home for /issue/<d>: Leaf route.ts; opened on leaf.estiva.app as QA-1 today, no file page and no "could not be found" within two minutes.
  • Readers compare hosts exactly, so another app's host on a Ship path is a plain link: the shared link reader (matchObjectUrl). Read in code, not tried on production.
  • Only Ship declares /issue/ and /project/ addresses; Leaf declares only /document/, Peek only /topic/ and /message/: each app's entry on origin/main.
  • A mention is decided at send and an edit carries none: spec C25 and §13.6.2.
