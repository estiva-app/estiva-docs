Osnova’s memory layer

Are Insights, Journal entries and Risks a feature of Ship’s projects, or the memory layer of Osnova itself, which any app’s file can have, marked from any conversation or block and read by every app and agent? And if they are the memory layer, what does every app agree on, and what is each company’s own?

What you said today, asked about their statuses:

“I think that’s where the discussion about Notion like simple dbs should happen. Basically, I think the protocol should define high level Highlights: Insights, Journal logs, and Risks, but there probably should be some flexibility. This is definitely not just about Ship. If somebody build a HR app and there is two file types: open position and candidate. Those highlights can be related to that. Insights about position, update on position, risk about certain position… I want to make sure that we are treating this as basic stone of Osnova protocol and broader Intelligence layer (the memory layer)”

Today

No app offers Mark yet, and no item is on the relay. The project being shaped prototypes the three as tabs on a Ship project, marked from a Peek message or a Leaf block, from your sketch.

What is already decided, all by you and all Accepted:

  • Three shared types, Insight, Journal entry and Risk, which any app reads and writes as it does an Issue, each item a file of its own (13 Nov). The record is titled “what a project learns, decides and worries about”.
  • Statuses: a shared start, each type’s own end (13 Nov): every item starts Proposed or Rejected, then Accepted (a Risk: Open), and ends Outdated, Superseded or Resolved. Each company names its own statuses under them, as for any type. Turned down that day: “template databases each company reshapes”, because two companies’ Risks would no longer mean the same thing.
  • An item is filed in one team and is about an issue, else a project, else an Initiative, or is just the team’s (today, merged).
  • An item shows its source as it was marked, and the relay refuses one its readers cannot read; a Journal entry’s decider becomes a member of it; who may accept is each company’s rule, and every item starts at Proposed (all today, merged).
  • Your answer today that apps name the types they open in their own listing is an Accepted record, merged today (estiva-docs#449).

So the types are already Osnova’s, not Ship’s. What is still Ship-shaped is what an item can be about (only Ship’s three levels) and where its lists show (Ship’s tabs).

Why it reaches beyond this project

  • It decides what Osnova is for an outside company. A company that builds an HR app either gets a memory on its own positions and candidates for free, or builds its own notes type beside ours, and the company then has two memories no agent reads as one.
  • An agent asks one memory, whoever wrote it. “What did we decide about this position?” works the same way as “what did we decide on this project?”, or it does not.
  • It answers part of two Accepted records. Today’s “about an issue, else a project, else an Initiative” would become Ship’s case of a general rule. And “some flexibility” asks whether the 13 Nov statuses still hold; this page says they do, with the flexibility as a company’s layer on top.
  • A real reason to keep memory out of one app: on 9 September Katerina’s marks were lost, because they lived only in Peek’s old database, which was deleted. They never reached the relay.

Two-way today, one-way once items exist. Nothing is on the relay yet, so every call here costs nothing to change now. Once items are written, the meaning of the three types is one-way: a shared type changes only compatibly, and a breaking change is a new type (13 Nov record). Per call: widening “about” later is a compatible change, but narrowing it after an HR app has written items about candidates is not. Stage words are written on every status change and stay in every item’s history. A core field can be added later; removing one is a new type.

The stage words, under A

Today every type shares four stages, open, started, done and dropped, and a reader treats any other word as “this app does not say”. Two ways to name the items’ stages:

Status (13 Nov)W1 · reuse where the meaning is the sameW2 · all new words
Proposedproposed (new)proposed
Accepted; a Risk’s Openaccepted (new)accepted
Outdatedoutdated (new)outdated
Supersededsuperseded (new)superseded
Resolveddone, as an issue’s Doneresolved
Rejecteddropped, as an issue’s Cancelledrejected
  • W1 · reuse recommended: one meaning, one word. Any app that already counts stages, an outside one included, counts a resolved Risk as finished and a rejected item as dropped without learning anything. Today’s apps read the four new words as “does not say”, which is safe: nothing is miscounted.
  • W2 · all new: items never mix with work in any count, but there are two words for “dropped”, and a generic app counts nothing until it learns six.
  • Risk’s “Open” in either case: its stage is accepted, not open. On an issue, open means “not started” (Ship’s Todo); if a Risk’s Open carried that stage, every app would count a watched Risk as work nobody has begun. The label “Open” can stay as Ship’s default; labels are the company’s, and Katerina’s look.

What this means for the project being shaped

  • The build still starts with Ship, Peek and Leaf, from your sketch: Mark in Peek and Leaf, the lists on Ship’s projects. The HR app is on this page, not in the build.
  • Under the recommendations, three things are written differently, not built bigger: “about” takes any file, with Ship’s roll-up said in Ship’s listing; the stage words go into the SPEC part the project already owes; the core fields stay the 13 Nov list.
  • A topic’s or a page’s own lists in Peek and Leaf are allowed by the protocol; whether the prototype draws them is a scope call. Lean: a Later line, unless the Universal Navigation thread makes you want it now.

How others do it

  • Notion: any page relates to any database row, and its Status property sorts every status into three fixed groups that each workspace names. That is option A for a, and A for b. What breaks for us: Notion’s relations live in one vendor; here every app must read them.
  • Salesforce and HubSpot: notes, tasks and activities attach to any record, a contact, a deal or a custom object, with one timeline on each. That is a-A with c-A, inside one vendor.
  • Linear and Jira: each team names its statuses, each in a fixed category. Our existing rule for every type.
  • Upstream Nostr highlights point at any event or address, and carry no status. Any file, but no accept and no lifecycle.

The questions, each with a recommendation

Asked together as one scenario: c only arises if a is A, and the stage words only if b is A.

1 · Can an item be about any file of any app?

Yes (A). Ship’s issue, project and Initiative become Ship’s case of a general rule, and each app says how its own files roll up. It is the protocol shape you described, “not just about Ship”, and the only one in which an outside app does not grow its own memory beside ours. It supersedes in part today’s record: its “about an issue, else a project, else an Initiative” line.

2 · Do the 13 Nov shared stages still hold, with the flexibility as each company’s layer?

Yes (A). Shared stages are what lets an agent tell what a team believes from what was only suggested; the flexibility you asked for is the company’s statuses and fields, and later the database, on top. Each company defining everything (B) is the option you turned down on 13 Nov, and it breaks the memory for every app but the one that wrote it.

3 · Which stage words?

Reuse where the meaning is the same (W1): Resolved is done, Rejected is dropped; new words only for proposed, accepted, outdated and superseded. A Risk’s Open is at the accepted stage, never at an issue’s “open”.

4 · Which app shows an item’s lists?

Every app that opens the file it is about (A). Memory sits where the work is, in every app, and no company needs Ship to have one. For this project, Ship draws them first.

5 · Which fields can every app rely on?

The 13 Nov list (A): title, summary, details, sources, team, about, status with its stage, kind of entry, decided by; everything else is a company’s own. And an item typed by hand may have no source.
