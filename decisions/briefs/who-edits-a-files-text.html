Who edits a file's text

A brief for Miky · 19 Oct 2026 · from the issue you filed today, "Sidebar should not show Peek Topic and should allow to edit Ship Project/Issues" · it reopens part of a call you made on 14 Oct

The question

When a file has text — a Leaf page, a Ship project's or issue's description — may any app that has an editor open that text and change it, or does only the file's own app offer the editor?

And behind it, the idea in your issue: is a file something that grows — a topic gains a text and becomes a page, a page gains a status and an assignee and becomes an issue — or are those three different kinds of file that never turn into each other?

Today

Open Leaf and the tree lists every file in your Folders: 24 Peek topics, 29 Ship projects (with about 150 issues under them), and 11 Leaf pages. Only the pages do anything. A topic or an issue opens a screen that says "Open in Peek" or "Open in Ship". That is your complaint: most of the tree is noise.

That is how it was decided on 14 Oct, in "A document is its own type of file": a Leaf page and a Peek topic are two types ("Peek Topic is Peek Topic. Leaf doc is Leaf doc"), neither turns into the other, the app that owns a type decides how it is drawn and opened, and only that app offers the text editor — Peek and Ship show a Leaf page read-only. The record also says, in its first paragraph, that Leaf's tree shows a topic as a topic that opens in Peek.

Underneath, the relay already treats text one way for every file. A Ship issue's description and a Leaf page's text are the same thing: one "description", which anyone in the file's Folder may change, from any app that is allowed to write changes. Leaf's sign-in is already allowed to, and the relay checks only that you are in the Folder, never which app's file it is. Ship's app listing even announces "describe this issue" and "describe this project" as actions other apps may take. So "only the owner edits" is a rule the apps keep, not one the relay keeps.

A topic, on paper, may have a text too: the Specification gives every topic a "describe" action. In practice none does. Of the 31 topics on the relay, not one has ever had a text, and Peek has no place to write or show one. Your issue describes a topic as "just an empty file with conversations attached to it", which is how it is used, but not yet what the protocol says.

The Specification already anticipates your Peek comparison. Peek says, in its app listing, "I show the conversation of every file", which is why every file opens in Peek. A second such role, "I show the document of every file", is reserved and unused.

Why it reaches beyond this ticket

  • It sets what "owning a file type" means for every app, ours and an outside company's. Either owning a type means "your editor is the only one", or it means "you decide what the file is called, what extra fields it has and where it opens, and its text belongs to everyone". A company that brings its own issue tracker learns from this whether Leaf (or their own wiki) will edit their issue descriptions.
  • It decides whether a topic, a page and an issue are one kind of thing at different stages, or three. That is the file-evolution idea, and it reaches the shape of every file on the relay.
  • Door. Letting any editor write text (option B) is a two-way door: nothing new goes on the relay, and taking it back is an app change. Making files grow from one type into another (option C) is one-way: it changes what a file's address is, so every link, comment and card written afterwards depends on it.

Options

A — Keep the record: each file is edited only in its own app

Leaf is a document app. Its tree shows Leaf pages and stops showing other files (topics, projects and issues alike), or keeps them as "Open in …" rows as today. Writing an issue's description stays in Ship.

You see: a clean Leaf tree of pages only. To fix a typo in an issue's description you go to Ship. An outside company gets: a simple promise — their files are edited only in their app. Locks in: nothing new; the record holds.

B — Leaf is to text what Peek is to conversation: it opens every file whose app shares its text

A file's text is shared. An app with an editor (Leaf, and later anyone's) may open and edit the text of any file whose own app says its text may be written by others, as Ship's listing already says for projects and issues. The file's own app still decides what it is called ("Issue"), its extra fields (status, assignee, lead) and where "Open in …" goes, and it can keep a file type's text to itself by not offering it. Leaf takes the reserved "document of every file" role, the way Peek holds "conversation of every file".

A topic is a conversation and nothing else: it stops offering a text on the wire, which costs nothing, because none of the 31 ever had one. So Leaf leaves topics out by the rule, not by a filter it has to remember. Topics, pages and issues stay different types, and nothing turns into anything else.

You see: open LEAF-13 in Leaf, rewrite its description in Leaf's editor, and Ship shows the new text. The same rule would let Ship (and Peek, if you want) edit a Leaf page's text — that undoes your 13 Oct "read-only in Peek" scope line, so it is a question of its own below. An outside company gets: the text of every file is a common layer, and they choose per file type whether to share it — the same "declare what others may do" pattern Nostr apps already use. Any editor in the workspace, ours or a third one, works on the descriptions they share. Locks in: an owner can no longer count on being the only writer of its text, so an app that needs the text in a special form (a template, required headings) has to cope with edits made elsewhere. That is already true on the relay today.

C — Files grow: a topic can gain a text, a page can gain fields

Your issue's full model. There is one kind of file. A topic is a file with only a conversation; add a text and it is a page; add a status and an assignee and it is an issue. Leaf shows any file with text, Ship any file with Ship's fields, Peek every file. Converting is something a person does, and the file keeps its link, its conversation and its place.

You see: a Peek topic that grew a long discussion becomes a Leaf page with one action, and a page becomes a Ship project when the work starts, without a copy. An outside company gets: Notion's model — every object is a page with optional properties — which is easy to explain. But on the relay a file's type is part of its address today: a topic, a page and an issue are told apart by the number in their link, and that number is also how an app claims "these files are mine". For a file to change type and keep its link, the type has to move out of the address into a field, and ownership has to be claimed by that field instead. That rewrites how every app finds, names and opens files: every comment, every link someone wrote and the Folder's listing point at the old address. It reverses "no conversion, in either direction" from 14 Oct, and its first step — a topic with a text is a page — is the shape you turned down that day ("Peek Topic is Peek Topic"). Locks in: one-way once files are written that way.

How others do it

  • Notion is C: a database row is a page with properties, and any page can gain them. It works because one company owns the one app; nobody else writes Notion pages.
  • Linear, Jira are A: an issue's description is edited only in the tracker.
  • Google Workspace is A by file type (a Doc opens in Docs), with "convert" making a copy rather than changing the file.
  • Nostr (NIP-89) names one app per kind for opening; any client may still publish any kind. B is the honest reading of that: the owner picks the opener, not the only writer.
  • AT Protocol types every record by its schema name, permanently; a record never changes type. Changing type there is a new record.

Recommendation

B: Leaf becomes to text what Peek is to conversation. A file's text is shared with any editor app wherever the file's own app offers it (Ship already does), the owning app keeps its name, its fields and where it opens, and a topic is a conversation with no text. Topics, pages and issues stay three types.

It is the shape the relay already has, stated as the rule for apps too: every file's body is one shared text that any Folder member may change, and only the apps pretend otherwise. The owner's opt-in is how Nostr apps already declare what others may do with their files, so an outside company keeps control per file type. It is your Peek comparison made exact, using a role the Specification already set aside. And it gives you the part of file evolution you feel today: a Ship issue is a document with fields, and you can write it in Leaf.

Making a topic text-free is what lets Leaf's tree follow a rule: Leaf shows files with a shared text, and a topic has none. It matches how every topic is used today and how your issue describes it.

I do not recommend C as a protocol shape. It works in Notion because one company writes every page; on an open protocol, a file's type is how strangers' apps find and claim it, and moving it out of the address changes every app's lookup to buy conversion. If "turn this topic into a page" becomes a real moment, it can be an action that makes a new page and links the old topic, without changing what a file is — asked then, with that moment in hand.

If B: two smaller calls

  • The mirror. B lets Ship and Peek edit a Leaf page's text too. Do they offer it now, or does Leaf go first and they follow later?
  • A page filed under a topic. A Leaf page can sit under a Peek topic (none of the 11 pages does today). With topics gone from Leaf's tree, does that page move up to the Folder's level in Leaf, or does its topic stay as a plain row so the page keeps its place?

Checked

  • Every file's text is one "description" that any Folder member may change through any app that writes changes — Specification, "A file's text: the description field" (on origin/main).
  • Leaf's sign-in may already write those changes — Leaf's kind list (src/relay/client.ts) and Estiva ID's seed for Leaf.
  • Peek writes no text on a topic: "A topic has no description" (peek-app ForeignObjectWidget.tsx). The Specification gives a topic a "describe" action; on the relay, 0 of 31 topics have a text, at creation or by a later change (relay read as the agent, today).
  • Ship's listing offers "describe issue" and "describe project" to other apps (estiva-ship src/nostr/manifest.ts), and the relay checks only Folder membership on a text change, not whose file it is (buzz ingest rules, per the protocol pre-review).
  • Leaf would read the same text Ship shows: both fold the latest change, then the root's own text (interop's projection and Ship's fold, per the protocol pre-review).
  • The "document of every file" role is reserved in the Specification and declared by no app ("aspect", §7.8).
  • Leaf's tree draws every non-page file as a labelled row that opens elsewhere — leaf src/folders/tree.tsx.
  • Counts from production today: 24 topics, 29 projects, 152 issues, 11 Leaf pages, none of them filed under a topic (Ship and Peek listings and a relay read, as the agent).
  • A file's type is part of its address and is what an app claims to own — Specification, "The document", and NIP-89.
  • Not yet verified: that the relay accepts a Leaf-signed change to a Ship issue's text on production. To be probed before the build ticket is written.
