How a topic lists its files

For Miky. This stage writes the answer to the relay, so on your answer it becomes a decision record in estiva-docs, and your merge accepts it. The rest of the navigation rework still has no records, as you said on 28 Oct.

Decided, 30 Oct (Miky, in the shaping session): A, the topic keeps its list. In his words: "Topics is just lens. The file still lives in Folder (in future we will rename to Team). Topic is group of files across different teams" — such as a design plan, an engineering plan and a marketing plan around Widgets, from Design, Engineering and Marketing. "Also one file can be in multiple Topics": a Company Strategy / Roadmap document gives the context for Widgets and is listed in many more topics.

When someone puts a Ship project or a Leaf document into a topic, whose list is that: the topic's, or the file's? Or is there no list at all, and a topic's files are just the ones its conversation links to?

Settled already: a topic is a file, not a group (29 Oct). It lists files from any team, and listing grants nobody anything (concept page, 28 Oct). A listed file opens in its own app, and a file doesn't filter the topic (meeting, 30 Oct). A file is named by its id everywhere, and that includes a listing (record, 29 Oct). This brief is about who writes the list and where it is kept.

Today

A topic has a title, a summary, a parent, its members and its conversation, and nothing else. It cannot list files. The only thing that lists files is a Folder: the relay keeps its listing and refuses a listing command anywhere else. Peek's Topics column therefore draws every file you have joined as its own row, so a topic, a Ship project and each of its issues all sit on one level (Katerina and Miky, 7 Oct: "get rid of the tree structure"). Nothing anywhere says "this file is in topic X".

Why it reaches beyond this stage

  • It is the first thing besides a Folder that holds other files. Ship's Topics page, Leaf's Topics section, the Desk and Main/All later all read this list. So does any outside company that wants its own files in a topic.
  • It decides who curates a topic. Either the people running the topic choose what is in it, or the people who own each file do.
  • It sets the pattern for future "collections", such as a release or Grants, which list files across teams.
Mostly a two-way door at today's size. We have 25 topics and nothing private. Switching shapes later means rewriting each topic's entries once: tens of small events, signed by the agent or by their original authors. It gets harder once outside companies write entries we can't re-sign, or once private teams make some entries unreadable to whoever migrates them.

Options

The examples use the real Widgets topic and its files, as scenario 7 of the concept page tells it: two Ship projects and Katerina's Leaf document "Testing Widgets".

A · The topic keeps its list recommended

Each listed file is one entry on the topic: added or removed by anyone in the topic's team, and signed by whoever did it. This works the way "who is on this file" already does. Each entry names the file by its id, so any app can ask the relay "which topics list this file?" and get an answer.

Miky sees
On Widgets he picks Add file and chooses Testing Widgets, even though it is Katerina's. It shows under Widgets in Peek's Topics column, and her document says "Topics: Widgets" in Leaf.
Katerina sees
Her document is in a topic she didn't put it in. She can remove it from there, but only if she is in the topic's team, and today everyone is.
Outside company
Lists its own files in our topics without changing its types. To show "Topics: …" on its own files, it asks the relay one question.
Could go wrong
A file can be listed somewhere its owners never chose. Today it is only a locked row, never its title, for someone who can't open it. A deleted file leaves an entry that points at nothing, which apps must skip. Two people adding and removing the same file at once: the later change wins, as with members.

C · The file says which topics it is in

Each file gets a "topics" field, set by whoever may edit the file, the same as its title or status. A topic's files are whatever files name it.

Miky sees
To put Katerina's document in Widgets he needs to be able to edit it. If he can only read it, he has to ask her.
Katerina sees
Nothing lands in a topic without one of the file's editors choosing it.
Outside company
Must add the field to each of its own types, or its files can't be in any topic.
Could go wrong
Once teams are private, a topic led by one team can't gather another team's files without that team's help, which is exactly what a release or Grants needs. Ship, Leaf and every future app each build the same field. Every listing change also counts as a change to the file, so it shows in the file's history and activity.

D · No list: a topic's files are the ones its conversation links to do less

Nothing new is stored. Link a file in a topic's message and it shows as one of the topic's files. Messages already record the files they mention.

Miky sees
Widgets gathers whatever anyone linked, including Weekly Plans, mentioned once in passing. He can't take it off the list without editing an old message.
Katerina sees
A document she links in the topic's conversation joins its files, whether she meant it to or not.
Outside company
Nothing new to build or agree on.
Could go wrong
The list mixes curated files with passing mentions, and it grows forever. A file linked in an old message stays in the topic's files with no way to drop it. Mentions inside a file's own threads don't count, so the list depends on where people happened to talk.

Not offered: the relay keeping a topic's list the way it keeps a Folder's. That would make a topic a group, which reverses your 29 Oct call (a topic is a file, not a group) and the Accepted record that only a Folder gets a relay-kept listing.

How others do it

  • Linear Initiatives: the initiative holds its list of projects, and anyone who can edit the initiative adds one. A project shows its initiatives. This is A.
  • Notion relations: a property on each page, set by whoever can edit that page. This is C, and it is two-sided only because Notion syncs both sides in one database, which we don't have across apps.
  • Slack channels: "files in this channel" is worked out from messages. This is D, and it is why a channel's Files tab is rarely useful.

Recommendation

A, the topic keeps its list. A topic is "what the company is focused on now", and the people running it are the ones who know what belongs in it. Because listing grants nothing, a file's owners have nothing to protect by being asked first. It is also the shape you already chose for every file on 30 Oct: a file is its fields, each change signed by whoever made it. That means the list moves untouched when topics move to the new file shape, which is what made "topics now, the record later" safe. C asks every app and every outside type to carry a field so that a topic can work. D gives a list nobody can tidy.

Checked

  • Only a Folder has a listing. The relay refuses a listing command unless it is in a Folder (buzz nfb-demo-kinds, crates/buzz-relay/src/handlers/side_effects.rs: "a {t} channel is not a Folder"). A topic is a kind:30840 with no listing (SPEC §6.7).
  • A topic's changes are per field, signed by whoever acts, in the topic's own Folder, and member:<p> is already a field per person (SPEC §6.7 "Changes", §11.8).
  • A file is its fields, each change signed by whoever made it, and nothing that names a file is re-signed when it moves (record a-file-is-its-fields-each-kept-in-order-by-the-relay, Accepted 30 Oct).
  • Anything that lists a file names it by its id in the small tag (record a-file-is-named-by-its-id-in-a-capital-and-small-tag, Accepted 29 Oct). No app reads or writes that tag yet; the relay writes it in a Folder's listing (buzz#38) and filters #o on any event. Whether it stores a 1851 carrying o is probed first in the build.
  • Peek's Topics column draws every joined file flat (peek-app src/components/views/FileTreeView.tsx, JoinedFileRows). Nothing shows "which topics list me" in Ship or Leaf (survey of origin/main, 30 Oct).
  • 25 topics on production today (peek topics, 30 Oct; 32 on the relay, 8 of them QA's, recounted later that day). Nothing is private, so access cases are latent.
  • Not verified: the relay's answer time for "which topics name this id" at Miky's scale. It is a one-letter tag filter, which the relay supports, but it hasn't been measured.
