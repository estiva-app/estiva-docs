May the relay tell an app when things changed, without sending what changed?

To put your topics in order, every app needs to know when something last happened in each one. Should the relay be allowed to answer that question with just the times, instead of handing over every signed change so the app can read the time off it?

Today

Peek, Ship and Leaf all order your topics the same way: by the last time anything happened in a topic or in the files it lists, deep. That includes a comment, an edit, or a new issue filed in a listed project. You decided that rule on 6 Nov ("Where anything moved").

To learn those times, each app asks the relay for the newest change of every file involved, and for every issue under each listed project. A Nostr relay can only answer with whole signed events. So a time costs the whole event: when the newest change is a saved text, the whole text comes along (up to 0.15 MB for one file), and finding a project's issues brings each issue with its text.

Measured this morning as you, on Leaf's Home: 2.2 MB for the order alone. 0.9 MB is whole issues and pages found under 27 listed files, 1.3 MB is the newest change of about 590 files. Ship pays the same on a project page. It grows with every issue filed and every long text saved.

Why it reaches beyond this ticket

Until now, every answer the relay gives about files is the signed events themselves. The one exception is search, where the relay adds a note on which words matched, and only beside the signed files it found. This question is whether the relay may also answer with its own statement ("this file's text last changed at 09:14"), with no signed event beside it.

That sets what any Nostr-for-Business relay may answer and what any app may rely on. Any later "recently changed", "updated" column or inbox could use the same answer.

It is a two-way door for the data: nothing new is written to the relay. A relay advertises the new read, and an app that doesn't find it reads whole events as today. Undoing it means dropping the read. The precedent is the part that sticks: once one app relies on times from the relay, the next feature will want them too.

The picture

Options

A. The relay answers "when did each part of these files last change"

You and Katerina: the same topics in the same order, from a few KB per topic instead of whole issues and texts. Opening Leaf's Home loses about 2 MB, and a project page in Ship about as much. Filing more issues or writing longer texts no longer makes the order heavier.

An outside company gets a general read: "for these files, when did each part last change, and when were they last commented on". It works for any "recently changed" list, not only our topic order. The rule for what counts (a rename does not, a comment does) stays in each app's shared code and never moves into the relay.

What could go wrong: the answer isn't signed, so an app trusts its own relay for the order. That is fine for ordering, but nothing should ever be decided on a time from it. The answer has to follow exactly the read rules the events would: a project's text edit time goes only to people who can read its team, as its text does today, or the time itself would leak that someone is editing. A stale tab keeps reading whole events, which still works.

B. Keep every answer signed, and make the files lighter instead

You and Katerina: about 0.9 MB less per open, because issues and pages no longer carry their text inside them. The 1.3 MB of saved texts stays, because the newest change of a file is still often a whole text. The Done-when is missed.

An outside company keeps the purest rule: every byte a relay sends is something someone signed. It must also write every type this way.

What could go wrong: every issue and page already on the relay has to be rewritten or migrated, and that is one-way. Every app that reads an issue's text from the issue itself breaks until it changes. It solves only part of this problem.

C. Do less: keep reading whole events, and accept the cost

You and Katerina: no change. The order costs 2.2 MB on Leaf's Home today, about 3% of that open, and it keeps growing with every issue and every long text. The ticket's Done-when (no more MB than before topics were ordered) is dropped.

An outside company: nothing new to learn.

What could go wrong: it is the read most likely to grow quietly. The device copy (NIP-77, decided 4 Nov) would later make a second open cheap, but not the first one after a reload. The relay doesn't support it yet.

How others do it

  • Upstream Nostr: COUNT (NIP-45) already lets a relay answer with its own unsigned statement, a number, instead of events. A times answer is the same kind of thing.
  • Matrix: the newer "sliding sync" orders your rooms by a server-supplied recency stamp without sending the rooms' history. That is option A's shape, on a federated protocol.
  • Slack, Linear, Notion: the server simply says "updated at". It's trivial when the server is trusted, as our relay is for the company that runs it.

Recommendation: A

It's the only shape that makes ordering cost a few KB per topic and keeps it there as work piles up. It is also the shape an outside company would want for its own "recently changed" views. The relay states only a time, under the same read rules as the event behind it. The rule for what counts stays in the shared code, so no app's behaviour moves into the relay, and an app that finds no such read falls back to today's.

It extends the line we drew for search, from "a note beside the signed files" to "a statement on its own". The reason that is acceptable: a time decides only the order of a list, never who may do something or what a file says.
