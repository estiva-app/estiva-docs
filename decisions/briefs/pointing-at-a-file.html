Pointing at a file

Decision brief, 29 Oct 2026 · The one open part of D1 in the Accepted record Every file is an artifact the relay keeps in order, for the project on the architecture page, which draws the whole project; this page draws only what points at a file. About five minutes.

The question. When a comment, a mention, a Folder's list or a chip points at a file, what does it write, so that any app, ours or an outside company's, can find the file and tell "about it" from "mentions it"?

Today

A project is named by its address: type number, author's key and id. A comment carries it as "about it", which apps show as the conversation. A message carries it as "mentions it", shown under Mentioned in, and its chip is the same address in Nostr's link form. The Folder's list, who is on it, unread state, cards and block links copy it too.

Already decided. On 29 Oct you chose (D1 a, brief "What a file is") that one reference names a file everywhere: its id, "in one single-letter tag". The letter was left open. On 14 Oct you chose that a link is stored as the URL a person wrote; only a chip picked from the [ menu or Cmd+K still saves the internal form.

What the protocol review found, checked: one marker is not enough.

  • "About it" and "mentions it" differ by the marker's case: a capital letter for the file a comment is about, a small one for a file it mentions. Nostr's comments need both cases. So the reference is a pair: one letter, two cases.
  • The chip in the text has no form for the new file. It encodes a type number and an author's key, and a file the relay keeps has neither in its name. A typed or pasted link, like ship.estiva.app/project/plan-<id>, carries only the id and keeps working.

Why it reaches beyond this project

  • One rule for every app and every outside company that points at a file, for projects first, then issues, documents and topics. It is also what we ask Block and Nostr's comment standard to adopt.
  • One-way. Every comment, listing and chip written from this stage on carries it. Undoing it means re-signing each of them by its own author, as the September comment move did with keys from Estiva ID. Unread state only ever grows, so a wrong unread key stays for good.

Three options

1 · A new pair of markers that hold the file's id recommended

What you see. Nothing changes on screen. One thing differs: a chip picked from the [ menu or Cmd+K is saved as the file's link, so a copied message carries a link that opens, as a pasted one already does.

Outside company. Three plain questions, one meaning each: comments on this file, everything that names it, comments on any project. The same works for its own types, such as acme.candidate.

What could go wrong. Two proposals, to Block and to Nostr's comment standard; what they refuse we carry as our rule. A plain Nostr comment app shows no thread, but no business reader uses one. After a type converts, older comments still name the old type, so a comment's type is only a hint. A file's id looks like a Folder's id, so unread state needs a rule to tell them apart. A type whose app publishes no link has no chip in text. An outside app needs our link rules to draw a link as a chip, as already accepted on 14 Oct.

2 · Borrow Nostr's marker for things outside Nostr

What you see. The same as 1.

Outside company. Plain Nostr comment apps thread our comments, as comments on an outside thing, like a web page, that they cannot open. Every app strips an osnova: prefix. The type can only say "osnova", so nobody can ask for "comments on any project".

What could go wrong. A file on our own relay is filed as "content outside Nostr" in every event, in the standard we ask others to adopt. The type cannot go into the prefix, because converting would rename the file.

3 · Do less: keep today's address marker

What you see. The same in our apps. Picked chips keep the internal form, so the 14 Oct record stands.

Outside company. Every Nostr library reads this marker as "this author's latest save" and asks for Miky's saves only. A builder has to learn that this one number means something else.

What could go wrong. Nostr's base rule says this marker points at a record its author replaces; the new record is saved by anyone, in the relay's order. The same marker means two things, by reader, and the creator's key stays in every pointer for good. The 29 Oct record turned this name down, so 3 reverses D1. It saves no re-signing: every pointer is rewritten either way.

How others do it

  • Block's artifacts: one artifact names another by its bare id, as option 1 does, but in a long-named marker a standard Nostr filter cannot ask for, and with no "about versus mentions".
  • Nostr comments: the top of a thread is an address, an event or an outside thing. The new record is none of the three, so every option bends something.
  • Notion: a mention stores the page's id, and so does its link. One server reads it; on an open protocol a stranger's code needs a standard marker.
  • Slack: a pasted link stays a link and unfurls into a card, as you chose on 14 Oct.

Recommendation

Option 1. A new pair of markers holds the file's id. The capital one means "about it", with the file's type beside it, and the small one means "mentions it". A chip in text is the file's link.

For the protocol. One meaning per marker, and the SPEC's "about" and "mentions" rule carries over letter for letter. A builder asks three plain questions, for its own types too. Upstream it is the cleanest proposal: a fourth thing a comment can be about.

For the person. Nothing changes on screen. A picked chip becomes a link, which finishes your 14 Oct call that a file has one address people recognise.

Cost does not tip it: 1 and 3 re-sign the same events. Option 2 buys threading in plain Nostr comment apps, which no business reader uses, at the price of the wrong meaning.

Does option 1 keep the Accepted record?

No. It amends it in two places, so it needs a new record that you merge.

  • The record says "one single-letter tag". Option 1 is one letter in two cases, as the address marker is today, and Nostr filters treat the two cases as two markers. A builder following the record's words would lose "about versus mentions".
  • The record does not say what a chip writes in the text. Option 1 makes it the link, which changes one line of the 14 Oct record A link is stored as the URL a person wrote: a pick from [ or Cmd+K saves the link, not the internal form. That line's reason, "no link to keep", no longer holds.

Asking this page writes a Proposed record that supersedes those two parts and nothing else; your merge is the accept. Option 2 would amend it the same way; option 3 reverses D1.

Not asked here: chips already in old signed messages, republished or left dead. The architecture page marks it as a separate call.

Checked

  • "About" versus "mentions" is told by case: true. SPEC §6.4, protocol/SPEC.md:670-671, 692-698, 715-719 (estiva-docs origin/main bee5013): capital A is the comment's root, small a not equal to it is a mention. NIP-22 (22.md:13-14, 44, nips 400d157, 27 Oct) requires a capital root and a small parent, each with its K/k.
  • A chip in text encodes the type number and the author's key: true. fileReference builds nostr:naddr from kind:pubkey:d (estiva-foundation packages/conversation/src/references.ts:278-280), and encodeNaddr writes the author and kind (packages/protocol/src/nip19.ts:276-300). An editor's link chip resolves to the same form (packages/protocol/src/embeds.ts:474-480). In a description it is a reference mark with that URI (SPEC §13.1 :3404, §13.3 :3726). An artifact is identified by "(community, d)" and "is not a NIP-01 addressable event" (buzz nfb-demo-kinds 7764733, docs/nips/NIP-AR.md:55), so no naddr names it truly.
  • Typed links survive: true. Ship declares /project/<slug>-<d> and /#/project/<d> (estiva-ship src/nostr/manifest.ts:897-900), resolved by the id (SPEC §7.7 :2325). Each line's third field says the old type number 30850 and must change with the move.
  • The 14 Oct record: "one way to address a file: its URL" (decisions/a-link-is-stored-as-the-url-a-person-wrote.md:15); "a pick … still inserts the nostr: reference" (:49); drawing a link as a chip needs the app's link rules (:20).
  • Who is on a file is targeted by the address marker: ["a", F] ["field","member:<P>"] (SPEC §11.8 :3099). Block links and cards carry the address: part (§13.6.1 :4152), embed takes what a carries (§13.6.2 :4276). Unread state keys a file by its address and a channel by a bare UUID (§11.1 :2769-2770), so a bare file id would share the channel's shape. That is the rule option 1 still needs.
  • Option 3 breaks NIP-01: the address marker is for addressable or replaceable events only (01.md:80-82, 99), and NIP-AR says kind 45010 is neither (NIP-AR.md:55). Option 2's meaning: NIP-73 is "External Content IDs" such as ISBNs and URLs (73.md:8-12). For those, NIP-22's K holds a type word, not a number (22.md:46-49, examples "web", "podcast:item:guid"). Option 1's K = osnova.project follows that precedent.
  • Upstream practice: NIP-AR's example names another artifact by a bare UUID in a project tag (NIP-AR.md:28), and attaches a conversation by root (:44, 63). d and type never change there (:55). Converting is one of our three upstream proposals.
  • Letters: the NIPs README no longer has its standardized-tags table (nips 400d157). I grepped every NIP for ["x", instead. c is in NIP-34 and 66, f in 69, F in CC, n in CC, 66 and 87, and N in 66 only. None of o O b B j J v V w W appears. Our SPEC and relay use no o/O. The relay filters by any one-letter marker (buzz crates/buzz-db/src/store/event.rs:101-103).
  • Not checked: whether Block and the NIP maintainers would take O/o; whether the relay needs an index for #O/#o at Miky's scale (#a has its own fast path, req.rs:1116); how the relay treats a comment with no A/E/I root (its note says it scopes comments by them, ingest.rs:611-613; ours also carry the Folder, so the Folder gate applies); Notion's storage, which is from its public API as remembered.
