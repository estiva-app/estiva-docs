Should we prune our unit tests?

PEE-50 · Peek and Ship · measured 14 Oct 2026 at origin/main · about a 5-minute read

Short answer: keep them, and change how new tests get in. We planted 26 realistic bugs; the tests caught 23 and never broke on a harmless refactor. Pruning would save seconds of CI. The real problems are elsewhere: four gaps the planting found, tests that fail falsely when the machine is busy, and no step that checks whether a new test protects anything.

2. Do they catch bugs? We planted some

Following the research Miky brought: a test suite is only worth its keep if it fails on a plausible bug and stays green on a harmless refactor. So we planted defects modelled on bugs we have actually had (read state published partially, a move that keeps going after the add was refused, raw HTML in a description, a muted stream lighting a dot…), ran the suites, and reverted each.

Controls: 4 harmless refactors (renaming a private helper, reordering independent lines): 0 tests failed. The tests are not glued to the implementation.

Ship's scripts earn their place: 6 of Ship's 13 catches came only from the small scripts that run the real store against a fake relay and check the events it sends. They are 2,400 lines against 10,300 of vitest. Peek has no equivalent layer.

Found on the way: the suites fail falsely when the machine is busy. With a few agent sessions running at once (load 20–60), a full run produced up to 37 failures in tests unrelated to the change, all timeouts in screen tests; each passed when rerun alone. CI's quiet runners never see it. Our agents do: a red run that is not real teaches "rerun until green", which is exactly how a real failure gets waved through. Neither repo sets a test timeout, so it is 5 s.

3. What the research says, and what we took from it

  • Agent-written tests barely change whether an agent solves the task (study of six models on SWE-bench Verified). Writing more tests during a task is not where the value is.
  • Tests generated from existing code can lock bugs in: they assert what the code does, faults included (SciPy / Qiskit / pandas study: several times more "fault-enforcing" than "fault-revealing" tests).
  • What holds up: tests that check behaviour and contracts, a check that tests fail on plausible bugs, and end-to-end checks as ground truth.

Our suites mostly pass that bar already: they catch planted bugs and survive refactors. The risk the research names is real for us, though: nearly every test is written by the same agent that writes the code, and nothing checks the test itself. That is a process gap, not a suite problem. Both studies confirmed to exist; numbers taken from summaries, not the full papers.

4. Recommendation: the current tests

Do not prune broadly. One small project, about five issues:

  1. Close the four gaps the planting found (one test each).
  2. Fix false failures under load: a sensible timeout for screen tests and a worker cap for local runs, then re-run the planting on a busy box to prove it.
  3. Speed: Peek's device-copy test sleeps ~8 s on real timers on the slowest CI shard; switch to fake timers. Slim the file-page test's ~380 lines of mock setup.
  4. Targeted cuts (~75 tests, ~3%): Peek's tests of debugging instruments (~51; keep the few probe.mjs reads), near-duplicate command-launcher and relay-read cases. Ship's tests that restate constants, re-exports or CSS class names, a finished-rewrite parity check, and mocked-store write tests the scripts already cover at the wire.
  5. Give Peek a wire-level layer like Ship's scripts for its writes (Folder moves, comments, read state), where the planting shows the most value per line. Could be a Later line instead.

Why A + B + C: they check the test against a real defect, which is the one thing reading a test cannot tell you.
