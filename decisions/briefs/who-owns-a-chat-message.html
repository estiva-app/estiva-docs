Who owns a chat message

A brief for Miky · 15 Oct 2026 · from shaping "Decision records 2" · nobody has decided this before

The question

Is a chat message something Peek owns, or something the protocol defines for every app, the way a comment and a topic already are?

Today

A chat message is one shape. It is what you write in a Peek topic, in a DM, in a Folder's chat, and in a chat thread on a Ship project. Ship writes them as well as Peek.

When someone links to a message from a Ship issue or a Leaf page, the app asks the relay which app owns chat messages. Peek's app listing says "these are mine", so Peek's listing decides how the message draws there and where it opens.

Comments and topics already work the other way. Since September, the Specification says how a comment or a topic draws, and every app has that built in. Each one opens in whichever app says it handles conversations, which is Peek today.

Nobody decided that messages are Peek's. The claim dates from Peek's first app listing, and the Specification already says that an app like Peek, which shows a conversation about everybody's files, owns no kind of its own.

This came up because the project you just approved makes Folders belong to no app. A Folder's chat is chat messages, so the next question is whose those are.

Why it reaches beyond this ticket

  • It is the rule for every company's chat. Under one answer, a company that brings its own chat app has to replace Peek as the owner of messages in its workspace. Under the other, it writes the same messages any app reads, and only says it opens conversations.
  • It decides who may change what a message is. An owner can add fields and actions to messages through its own listing. With the protocol as owner, adding anything to a message is a change to the Specification.
  • Two-way door. No stored message changes either way; only Peek's app listing and the shared library do. Undoing it later means republishing one listing and changing the library again, and every app built in between would change twice.

The picture

Options

A. A message belongs to the workspace's chat app (Peek here)

  • What you and Katerina see: nothing changes. A message linked from a Ship issue draws as Peek describes it and opens in Peek.
  • An outside company: brings its chat app as the owner of messages in its workspace, once workspaces can name their apps. Its app decides how messages draw in every other app there.
  • Locks in: the Specification's line that an app like Peek owns nothing gets an exception for messages. Ship goes on writing a kind that another app owns.

B. A message belongs to the protocol, like a comment (recommended)

  • What you and Katerina see: nothing changes. The same message card, and it still opens in Peek.
  • An outside company: gets chat messages from the Specification alone. Its own chat app only has to say it opens conversations to become where messages open.
  • Locks in: Peek can't give messages anything extra in other apps on its own. A new part of a message goes through the Specification, as it does for comments.

Not an option here: whether a Folder's chat should be comments rather than messages at all. That belongs to the parked "Folders as labels" question and stays parked.

How others do it

  • Nostr (NIP-29): the group chat message is defined by the standard, and any client draws it. Peek owning it is the odd one out.
  • Matrix: a room message is defined by the spec, and every client renders it. Clients compete on how they show it, not on owning it.
  • Slack: messages are the platform's, and apps extend them through attachments the platform defines. That is closer to B, with the platform playing the Specification's part.

Recommendation

B: a chat message belongs to the protocol, like a comment. It is already a shared shape: Ship writes it, and the upstream standard defines it. Comments and topics already work this way, and the Specification already says an app like Peek owns nothing. An outside company then gets chat from the Specification alone, with no app to replace. You and Katerina see no change. The one thing given up, Peek extending messages on its own, is the right thing to give up for a shape every app writes.

Checked

  • A link to a message is resolved by asking which app claims its kind: interop projection.ts, resolveForeignEvent, lines ~3160–3195. Comments and topics resolve through a built-in instead (projection.ts:1874-1876).
  • The Specification says an app like Peek "owns none" (SPEC §7.8, on origin/main).
  • Ship writes chat messages: estiva-ship src/api/writes.ts:407 and src/nostr/events.ts:334. KINDS lists a topic message, a DM and a Ship project conversation as the same kind.

  • Not checked: how a linked message looks in Ship and Leaf on production today. With the 13 Oct card decision, it is a chip unless its author chose a card.
