Whose agent is it?

The question: where should it say, in a way every app can check, that “Claude (steered by Katerina)” is Katerina's — so that Peek can leave her own Claude's messages out of her Screener, as you decided on 4 Nov?

Today

Katerina's Claude posted an update on a Ship issue she is a member of. Her Screener showed it as news from someone else. On 4 Nov you answered: your own Claude's messages skip your Screener, like your own messages do.

Building that, the premise breaks: no app can tell whose agent wrote a message. Estiva ID already signs a small proof, “this agent belongs to Katerina”, with her key. But the agent hands that proof only to the relay, in a side channel, when it connects. The relay stores it privately and uses it for one thing: letting an owner delete their agent's messages. Nothing an app reads carries it. The name “steered by Katerina” is self-chosen, and the record on bots says apps never decide anything from a name.

Why it reaches beyond this ticket

This sets how any app, ours or an outside company's, tells “my agent” from “a colleague's agent”. The Screener is the first use. The same fact would decide whether an owner gets Edit and Delete on their agent's messages (today nobody does, by the record of 6 Oct, which names this exact change as what would reopen it), and whether a person's page can list their agents.

Door: mostly two-way. Saying whose agent it is publicly is not a secret today (the name says it). Options B and C can be withdrawn by Estiva ID republishing; option A leaves the proof on every past message for good, which is harmless but permanent.

Options

B · The agent's profile says whose it is (recommended)

Estiva ID adds the owner's signed proof to the agent's profile, where it already puts the “I am a bot” marker. Every app already reads profiles to draw names and avatars; it checks the signature and knows “this is Katerina's Claude”.

  • Katerina sees: her Claude's update makes no Screener row and no unread dot for her, in every app, including the ~1,200 agent messages already on the relay. Miky still sees it, as now.
  • Outside company: reads one standard tag on a profile and checks one signature with any Nostr library; no list from Estiva.
  • Could go wrong: in a folder shared with another company, their relay may not hold our agent's profile; their apps then treat it as anyone's agent (today's behaviour). If an agent ever changed owner, the new owner would “own” its old messages too (agents here are one per person, so this does not arise today).

A · Every message the agent writes carries the proof

The agent stamps the signed proof onto each message, the way upstream Buzz's own command-line client already does.

  • Katerina sees: the same, but only for messages written from now on; the old ones still light her Screener until read.
  • Outside company: the proof travels with the message, so it works in a shared folder on another company's relay with no profile lookup.
  • Could go wrong: about 200 bytes more on every agent message (half of all messages are agents'); the proof cannot be taken back off old messages.

C · Do less: leave it as it is

No app learns whose agent it is. Her own Claude's messages keep showing in her Screener like anyone's. PEE-79 closes as “works as designed”, against your 4 Nov answer.

  • Katerina sees: her Claude's updates as news, every time; she reads or dismisses them.
  • Variant considered and not offered: hide every agent's message from everyone's Screener. Then you would also stop seeing Katerina's Claude's updates, which is a different product than the one you chose.

How others do it

  • Slack: an app's messages say “sent using X”, and a user's own app acts as them; the server knows, every client is told. We have no server that tells clients, so the fact must be on something they read.
  • Upstream Nostr (NIP-OA, owner attestation): an owner-signed tag naming the agent's key; upstream Buzz puts it on every event (option A). Putting the same tag on the profile (B) is the same standard in a different place.

Recommendation

B — the agent's profile says whose it is. Ownership is a fact about the agent, not about each message, so it belongs on the agent, next to the bot marker Estiva ID already publishes there. It covers the history Katerina already sees, and it is what the 6 Oct record named as the way to give owners their Edit and Delete back later. A shared folder on another company's relay is the one place A does better; if that turns out to matter, A can be added on top without undoing B.

Then the rule everywhere: a message by an agent you own counts as your own — no Screener row and no unread dot for you, in Peek, Ship and Leaf. (Edit and Delete for owners stays as it is; that is its own call.)

Checked

  • Estiva ID signs the owner proof — estiva-id src/nostr/nip-oa.ts, test owner-attestation.test.ts.
  • The agent sends it only as a request header to the relay, never on an event — estiva-agent lib/agent/credentials.ts (x-auth-tag), scripts/owner-attestation.test.ts.
  • The relay keeps the owner server-side only; “no client can evaluate this” — SPEC §6.5, and the record on Edit and Delete (Accepted, 6 Oct).
  • Apps must not decide from the name — record “An agent says it is an agent in its own profile” (Accepted, 24 Sep).
  • Peek already reads every author's profile for names and the bot marker — peek src/api/screener.ts, people.ts; so B adds no new read in Peek.
  • The Screener and the unread dot share one rule by design — peek src/api/internal/screenerFold.ts.
  • Not checked: whether a shared folder on a second company's relay copies our agents' profiles (that feature is not built).
