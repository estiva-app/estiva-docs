1 · How a file says what type it is

The question. When a builder launches its own type of file, a candidate in an HR app, what does its first record look like? And do projects, issues, documents and topics change to look the same?

Today

Each of our four types has its own first record, its own number: one for a project, one for an issue, one for a document, one for a topic. Every field change after it names the file. No builder type exists yet.

On 29 Oct you decided types carry names, not numbers: osnova.project for the shared ones, acme.candidate for a builder's own, launched without asking anyone. That name rode on the whole-file save. Under C there is no whole-file save, so the name needs a new home: the file's first record. A comment that names a file already carries the type's name beside its id (the reference you chose on 29 Oct).

Why it reaches beyond this ticket

It is the first thing any builder writes. It decides whether a builder's type that several apps start using can become a shared type without its files moving. Once a builder's files are on the relay, every app reads that shape for good: one-way per file written. Moving our four types is one-way at the move.

The picture

A · The four keep their records, and every new type uses one named first record recommended

What you see. Nothing changes for Miky or Katerina. The HR app launches "Candidate" by writing named first records; Ship and Peek show one as a plain file with its title and fields. If a second company's app starts using candidates, the directory gets an entry and nobody's files move.

Outside company. One rule for every type it makes, plus a short fixed table: these four old records mean these four names. It never writes the old ones for a new type.

What could go wrong. Two shapes for files, forever: four by number, everything else by name. Every reader carries the four-line table. A list "everything of type osnova.project" has to look in two places if a project is ever written the new way, so the SPEC says projects, issues, documents and topics keep their own records for new files too.

B · Everything uses the named first record, and the four move to it

What you see. Nothing, after a move like the one C removed: an announced moment, agents stopped, every first record re-signed by its author.

Outside company. One shape for every file, no table.

What could go wrong. It brings back the one-way move C was chosen to avoid. Katerina has to sign in for hers; any author without a key held by Estiva ID leaves their files behind. Everything that names a file by its old address (comments, listings, chips) must then be read by id alone.

Do less · Keep the four, and decide a builder's type when a builder needs one

What you see. Nothing.

Outside company. Cannot launch its own type yet, which the directory promises ("launches with them, asking nobody").

What could go wrong. The SPEC rewrite this project owes leaves a hole exactly where the next builder starts, and "Apps declare their types to the relay" has no file of a declared type to point at.

How others do it

Buzz (upstream): one kind for every artifact, with the type as a name in a tag, so a builder never asks for a number: A's shape for everything new. Nostr's habit is one number per shared meaning, which is why our four have numbers; the kind registry keeps those. Notion, Airtable: one record shape whose type is a reference to a schema, never a new table type per customer.

Recommendation: A. A builder's type should become a shared one by agreement, a line in the directory, never by moving every file of it; only a named first record allows that. Keeping the four where they are is C's own principle, nothing that names a file is re-signed, and moving them would rebuild the one-way move you removed this morning for one gain: a four-line table readers no longer carry.

2 · Several fields changed at once

The question. When one action changes several fields, Claude setting an issue's title, status and text in one command, is that one change or several?

Today

The SPEC says one change sets exactly one field, because two fields in one change would need a rule for when only part of it applies. The agent writes one change per field. This morning's record says several fields changed together are refused together, so a half-applied change never shows, and leaves open how they are written.

Where it happens: the agent's edit with several flags; a status with its stage, if a save carries the stage beside the status (owed by the statuses record you accepted today); restoring an older value of several fields; a type change with its new fields.

Why it reaches beyond this ticket

It is the one rule every reader of changes must follow, ours and every builder's. A reader that only knows "one field per change" misreads the other shape. Two-way while only our apps write it; one-way once a builder's app does.

The picture

1 · One change may set several fields, each naming the change it follows recommended

What you see. Claude's three-field edit lands whole or not at all; History shows "Claude changed title, status and text" as one line. One field changed is still one change, as today.

Outside company. One rule: a change sets one or more fields. The relay accepts or refuses it as one.

What could go wrong. Every reader of changes learns the new form before any app writes it; old one-field changes stay valid. A wide change refused because one field moved costs the writer a re-read of all of them.

2 · Several one-field changes in a bundle the relay takes or refuses together

What you see. The same as 1, but History shows three lines.

Outside company. Keeps "one field per change" and learns a second shape, the bundle, which the relay opens and stores as separate changes.

What could go wrong. Nostr has no bundle: someone watching the file sees the three changes arrive one by one, so a half-applied state is briefly visible to watchers anyway. The relay re-publishes events it did not sign itself.

3 · Do less: each field alone

What you see. Claude's title and text land, the status is refused and the agent says so; for a moment the issue shows a mix nobody chose. A status and its stage would be one field, so they never part.

Outside company. Nothing new to learn.

What could go wrong. It changes one line of this morning's record ("refused together"). Every app that changes two related fields has to clean up a half-done change itself.

How others do it

Linear, Jira, Salesforce: one update carries the fields it changes and applies as one; Jira's history then lists each field. Notion: one transaction of several small operations, applied together.

Recommendation: 1. One act by one person is one signed event, which is Nostr's own unit, and History then reads as what the person did. It is the shape every tracker an outside company already knows, and the relay has one thing to accept or refuse, without opening bundles of events it did not sign.

3 · "Go back to Tuesday's version"

The question. When someone wants a file back as it was on Tuesday, what do they get: Tuesday's text, or Tuesday's whole file, every field included?

Today

On 26 Oct you decided every file gets a History panel: field changes are a list, text saves are versions you can open, and Restore writes the text back as a new save under your name. Issues have that panel; projects have none, and this project adds none. Under the whole-file shape, Tuesday's whole file would have been one save; under C it is worked out from the changes.

Why it reaches beyond this ticket

It says whether a restore may change fields other people changed since. Two-way: every change is kept, so a whole-file view can be added later on top.

Text and each field on its own, as decided 26 Oct recommended

What you see. History lists who changed which field; Tuesday's text opens and restores as a new save under your name. A status or a lead goes back by setting it. When projects get a History panel, it is this one.

What could go wrong. Someone who wants every field as it was on Tuesday sets them one by one.

Also the whole file as of Tuesday

What you see. A "Tuesday" view of every field and the text, and one Restore that sets them all, in one change (call 2, option 1).

What could go wrong. One click quietly undoes other people's unrelated changes made since, exactly what C keeps apart.

Recommendation: text and each field on its own. People bring back words, as Katerina's Claude did on "UI Guardrails" on 13 Sep; a field is set back by setting it. It is what you decided on 26 Oct and asks nothing new; a whole-file view can come later on top, since every change is kept.
