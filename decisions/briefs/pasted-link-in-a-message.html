What a pasted link becomes in a message

Decision brief · 14 Oct 2026 · Widgets project, ticket "Ship's comment box turns a pasted link into its chip"

The question. When someone pastes a link to an issue into a message, in Peek or in Ship, does the sent message keep the link they pasted, or swap it for Estiva's internal reference? Either way it shows as the issue's chip.

Today

  • Peek's message box turns a pasted issue link into the issue's chip. It sends the internal reference (nostr:naddr1…), not the link. You decided this on 13 Oct, at the kickoff of "The composer resolves a URL as you paste it". This ticket copied that line.
  • Descriptions keep the link. A pasted link draws as its chip, but what is saved is the https link. You decided this on 14 Oct: "everything should be unified about URL, so it's not confusing for users to address the same file with different things. URL is recognizable and understandable." That answer was recorded for descriptions only; nobody asked it for messages.
  • Ship's comment box does neither. A pasted link stays text until it is sent, then reads as a chip.
  • A gap found while checking: a Ship comment that holds a pasted link does not tell the issue it was mentioned. So the comment is missing from that issue's "Mentioned in" list, in both apps. Peek's messages do tell it. This gets fixed in this ticket whatever you choose.

Why it reaches beyond this ticket

This sets what every app, and any outside company's client, writes when a person pastes a link into a message. It is also the first message-side reading of your 14 Oct "URL is the one address" rule.

Mostly a two-way door. Every sent message keeps the form it was sent with. But readers in both apps already draw both forms as the same chip, and they must keep doing that for old messages anyway. So changing course later only means changing what the two message boxes write; nothing already on the relay needs rewriting.

The picture

Options

A. The message keeps the link, in Peek and Ship

Katerina pastes an issue link into a Peek message; she sees the chip. Later she selects the message's text and copies it into an email: the email gets a working link. The same paste into a description stores the same link. The message also carries the index tag, so the issue's "Mentioned in" finds it. Peek's message box changes to match. An outside company's client sees an ordinary link it can open, and draws a chip if it reads our apps' link rules.

Locks in: a message's chip relies on the app's link rules (which address belongs to which app). If an app ever moved its domain, old links would need the old address kept as an alias; the index tag still names the object either way.

B. Messages store the internal reference; descriptions keep the link

Ship copies what Peek does today. Same chip on screen. Copying a message's text gives nostr:naddr1… instead of the link, while the same paste in a description keeps the link. That split is exactly what your 14 Oct rule was against. An outside client needs nothing of ours to know what the reference names, and it survives a domain move.

C. The internal reference everywhere, descriptions included

One address again, but the hidden one. It reverses yesterday's description decision and the removal of "Copy reference".

How others do it

  • Linear / Slack / Notion: a pasted link is kept as the link and drawn as a mention or unfurl. The stored text stays the URL. That matches A.
  • Upstream Nostr (NIP-27): writes nostr: references in text. That matches B, but upstream has no app link rules and no web addresses for files. We have both, and we already keep the index in a tag.

Recommendation

A: the message keeps the link, in Peek and Ship, built in this ticket. It is the same rule you set for descriptions on 14 Oct. It also matches what the protocol already says about mentions: the text is what the person wrote, and the tag is the machine index. Since the tag carries the durable machine form, B's one real advantage (no link rules needed) is already covered. Doing both apps in one pass keeps the two message boxes from ever writing different things for the same paste, which is what this ticket is for.

Picking from the [ menu, or from Cmd+K, still inserts the reference as it does today. Those picks have no link to keep. If you want them to write the link too, that is a separate question.

Checked

  • Peek sends the reference for a pasted link: peek-app src/extensions/pastedUrl.ts, chipUriOf (origin/main).
  • Descriptions keep the link: estiva-ui src/LinkChips.ts ("Never a nostr: reference in its place"), and your 14 Oct line on "Choose a link's card in a description".
  • Ship's comment send adds the index tag only for a reference, not for a pasted link: estiva-ship src/nostr/events.ts ~402–411. Peek adds it for links too: peek-app src/nostr/fileConversation.ts ~582 (urlReferenceTagsAsViewer).
  • Both apps' "Mentioned in" find messages through that tag (Peek fileMentions.ts; Ship fold.ts).
  • Both readers already draw a bare app link in a message as its chip (shipped 14 Oct, peek#497, ship#287), and a link can carry a chosen card (SPEC §13.6.2).
  • On production as QA-1, Ship's comment box today keeps every pasted link as plain text: an issue link, an unknown link, a block link, and a link over selected words.
  • Not checked: how many existing Peek messages already store a link plus the tag (Peek has added the tag for links since 21 Sep). It does not change the choice.
