Where an edited comment is listed

A brief for Miky · 27 Oct 2026 · from "A link in a comment reads the same in every app" (Every app treats @, a link and an archived file the same) · its Done when asks for it; the protocol says the opposite today

When somebody edits a comment to add or remove a link to a file, does that file's "Mentioned in" follow the edit, in every app?

Today

A comment that links a file is listed under that file's Mentioned in, through a pointer the comment carries from the moment it is sent. An edit changes the words, the files and the cards, but by our protocol (2 Oct) it carries no pointer: what a comment points at stays as first sent. That was decided when an edit was "a correction"; on 26 Oct you decided an edit is the whole new message, for its files.

So today: add a link by editing and the file never lists the comment. Remove one by editing and Peek drops the row (Katerina's report, 8 Oct, fixed only for chips) while Ship keeps it. Leaf has no Mentioned in.

Why it reaches beyond this ticket

  • It decides what an edit says on the wire for every app, the agent, and any outside company: does the edit say what the message points at now, or only its words and files?
  • It is the same question for a person named by an edit (are they told?). That one is already decided: no, an edit never notifies (the urgent-mention record). Both options here leave it so.
  • Two-way door, with a gap. Readers can start or stop reading edits at any time. But under A, links added by edits in the meantime are never listed later: nothing on the relay points from them. Under B, going back to A just means readers ignore what edits carry.

The picture

Options

A · Do less: a comment is listed by what it first linked, while its words still link it

  • You see: you paste the wrong issue, edit it to the right one. The wrong issue stops listing you (good, in both apps now). The right one never lists you: to get there you post a new comment.
  • Outside company: nothing new to write; every reader must check the latest words before listing.
  • What could go wrong: the list and the text disagree in the direction nobody notices. A link fixed by an edit is invisible from the file it names, for good. The agent's own comments are edited too.
  • Done when changes: "edits each comment to add a second link: its card appears" (the card half already works).

B · An edit says what the message links now, the whole set, as it does for its files

  • You see: fix the link by editing and the right issue lists your comment, the wrong one stops. Same in Peek and Ship; agent edits too.
  • Outside company: writes on an edit the same pointers it writes on a send, and reads edits as well as messages when it lists mentions. Buzz's own desktop already reads pointers off edits, so it is the shape a Buzz-family app expects.
  • What could go wrong: a reader that does not know the rule ignores edits and lists what was first sent (today's behaviour, no worse). A deleted comment leaves its edits behind; a reader must list nothing for an edit whose comment it cannot read. Edits written before this stay pointer-less: a link added by an old edit is not listed. People are untouched: an edit still never notifies anyone.

How others do it

  • Slack, Linear, Notion: a backlink follows the current text; edit the link out and the backlink goes, edit it in and it appears.
  • Matrix: an edit carries the whole new content, and clients read mentions from it (they are told not to re-notify).
  • Buzz (our relay's upstream): its desktop merges pointers from an edit into the message; files come wholly from the edit, the rule you accepted on 26 Oct.

Recommendation

B. "An edit is the whole new message" then holds for what it links as well as for its words and files, so the list under a file says what anyone reading the comment sees. It is what people already expect from every tool they use, and it is the shape an outside company on Buzz already reads. A leaves a permanent class of comments that point somewhere nobody can find from there.

Checked

  • Our protocol says an edit carries no pointer (SPEC §6.8, "the indexes a body earns… stay as first published", 2 Oct, CON-25). No decision record states it except for people: an-urgent-mention-is-a-tag-beside-the-mention says an edit carries no person or urgent tag, and B keeps that.
  • Peek lists mentions by pointer on comments and chat messages only, and drops a row an edit took out, for chips only (peek-app src/nostr/fileMentions.ts:90, :209, PEE-48). Ship reads pointers and chips from the first version only (estiva-ship src/nostr/fold.ts:416).
  • The relay has no rule on pointers in an edit and lets only people who can read the comment read its edits (buzz handlers/ingest.rs, req.rs), so B reveals nothing new.
  • Buzz desktop reads pointers off edits (desktop/src/features/messages/lib/applyEditTagOverlay.mjs).
  • Not checked: how many edits on production add or remove a link today.
