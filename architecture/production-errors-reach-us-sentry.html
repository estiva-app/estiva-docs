Production errors reach us

Shaped, 2026-11-17 · Ship project · Goal: when an app or a server breaks on production, we know from the system itself, not because Miky or Katerina told us.

Today nothing reports an error: a crash is seen only by the person it happens to. This project adds one small reporter to every app and both servers. It builds a short report from a fixed list of fields and sends it through Estiva ID's server to Sentry, and Claude reads Sentry at set moments. Look at the Map first, then at what a report may contain.

A report may contain: the app and its version; the kind of error and where in the code it broke; one of our own fixed sentences or the relay's reason code; the kind of screen (never its address); the last few steps before the error, as kinds of screen and our own named actions; the browser; the person's public key; whether it is a person, a QA account or an agent.Miky, in Sentry. Claude, reading. Sentry the company, as the host.Nobody changes a report. Claude marks an error resolved once its fix ships, or reopens it, and nothing else. Sentry deletes a report after 30 days.The reporter in the person's browser, then Estiva ID's server before it passes the report on. Tested by planting text and reading what leaves the browser and what leaves our server.
A report never contains: message or document text, titles, file names, page addresses, what was clicked, console lines, request contents, or the person's IP address. An error's own wording is sent only with quoted text removed.Nobody outside the browser.—The same two checks and the same test.
Who can send a report. A signed-in person's app, through Estiva ID's server; the public key on the report is the one signed in. A crash on the sign-in page, before anyone is signed in, goes through a tightly limited door and is marked as not signed in.—Nobody outside can send: Sentry's address is held by our servers only.Estiva ID's server.

Checked

  • No app or server reports errors today: a search of origin/main in peek, ship, leaf, estiva-id and the relay's deployed branch finds no Sentry or similar library (17 Nov).
  • Peek wraps itself and its panels in the shared "Something went wrong" screen (src/main.tsx, src/layouts/PeekFrame.tsx), which only writes to the console (estiva-ui src/ErrorBoundary.tsx). The same search finds no such wrapper in Ship or Leaf.
  • Estiva ID is a server and sign-in pages in one repo (src/server.ts, web/), and every app signs in through it (record sign-in-is-plain-oauth). The relay is written in Rust and already writes structured logs.
  • The reporter is our own code with no Sentry library, so it adds no outside dependency to the shared packages (record 0002-foundation-packages).
  • The peek, ship, leaf and estiva-id repos are public, so readable stack traces reveal nothing new. The relay's repo is private.
  • Sentry's pages, read 17 Nov: free plan is one user, 5,000 errors a month, 30 days kept; the storage place is fixed at creation; a per-app cap is a paid feature; the standard library also collects console lines, clicks and addresses unless turned off.
  • Not verified: whether a free-plan account lets Claude read at all (the price list says "API: No", and lists Sentry's MCP access, which Claude could connect through, as included), and whether Claude's access can be limited to reading and marking an error resolved. That is milestone 1; if it cannot be that narrow, Miky is asked before anything wider is used.
