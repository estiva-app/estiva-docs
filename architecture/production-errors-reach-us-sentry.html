Production errors reach us

As built, 2026-11-19 · shaped 2026-11-17 · Ship project · Goal: when an app or a server breaks on production, we know from the system itself, not because Miky or Katerina told us.

Today nothing reports an error: a crash is seen only by the person it happens to. This project adds one small reporter to every app and both servers. It builds a short report from a fixed list of fields and sends it through Estiva ID's server to Sentry, and Claude reads Sentry at set moments. Look at the Map first, then at what a report may contain.

As built, the shape held, with four findings. The free plan is enough. Claude reads Sentry with a personal read token. A second token can write to errors, and the command sends nothing with it but an error's state, to mark an error resolved or reopen it (record error-reports-go-to-hosted-sentry-built-from-an-allowed-list). The account stores its data in Frankfurt. The reporter lives in the shared packages (@estiva-app/platform, error-reports.ts), and each app adds only a thin file that wires it in. It sends each kind of error once per tab, at most ten a tab. The relay reports from its own code, not from its logs on the box. A small module in the relay's fork turns each error log line and panic into a report and sends it straight to Sentry. Estiva ID's server does the same. Both servers send at most 3 reports of one error an hour (Estiva ID counts by kind of error, the relay by place in the code), 10 an hour and 50 a day. The trail is mostly screens for now. The allowed list has named actions, but the apps record only the screens opened, and the reporter adds "write refused" when the relay refuses one. A crash in Peek before anyone is signed in is not reported yet. Estiva ID's sign-in pages do report through the limited door. The Map, the Access table and Checked are redrawn to match.

Checked

As built, read on 2026-11-19 from origin/main of each repository and origin/nfb-demo-kinds for the relay, and on production as QA-1.

  • The reporter is packages/platform/src/error-reports.ts in estiva-foundation. Peek, Ship and Leaf wire it in with src/lib/errorReports.ts and src/lib/failureReports.ts, and Estiva ID's pages with web/src/errorReports.tsx. It has no Sentry library.
  • Estiva ID receives the apps' reports at src/http/routes/report.ts and builds them again from the list in src/domain/error-reports.ts. Its own faults go out through src/domain/server-errors.ts. The relay's go out through crates/buzz-relay/src/error_reports.rs.
  • On production, 19 Nov, as QA-1: a crash made on purpose in Peek, Ship, Leaf and Estiva ID's sign-in page reached Sentry within 10–35 seconds. The text planted in the address, the title, the page and the failing message was in none of the bytes that left the browser, and in none of the events in Sentry. No event holds an IP address. The same crash repeated 1,000 times in one Peek tab sent one report. A report with no sign-in was refused (401).
  • Estiva ID's server and the relay each have a test request that only a QA account may make. Each one's error is in Sentry, and the relay's panic too.
  • Sentry, 18 Nov: the free-plan account in Frankfurt answers a personal token's API calls. "Prevent storing IP addresses" and the data scrubber are on for the whole organisation. A report carries no session replay.
